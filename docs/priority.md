# Priority: leads answer however busy the machine is

A person's message is answered whatever the machine is doing (issue #421). This is how the core keeps it so.

## One memory budget, and leads and wardens never wait

One figure paces the Hive: each agent turn is budgeted `turn_mb` (240 MB by default) of memory (`core.MemBudget`). Before a turn starts, `Runs.launch` takes the Hive's cgroup limit (the lower of `memory.max` and `memory.high`; with neither, the machine's `MemTotal`) and what is in use there (the cgroup's `memory.current` less its inactive file cache; on the machine, what `MemAvailable` doesn't cover), and holds the turn while that leaves less than `turn_mb` for it and for each turn launching beside it; an executor module with room takes it instead. The work module starts waiting briefs the same way, in line order, while the budget has room for another turn (`admit`). A lead's turn, and a warden's or tribunal seat's, never waits (`Run.NeverWaits`). There is no strain hold, ramp, pace, IO hold, `max_workers` or heavy-command lease any more; checks run at most `max_checks` at once.

## Main's measure gets the CPU

The score that keeps or reverts every merge is read from main's measure, so it is the one check the machine's load must not starve (issue #2169: at load 109 on 20 cores on 10-30, hive main's measures were cut off at their limits, and main went 17 hours and about 70 merges without a score).
While the improve module measures main (`work.MeasuringMain`, which calls `core.Effects.Measuring`), that commit's checks run at `core.MeasureNice` (4), under the leads and over every other run's turns at 10, not at `CheckNice` (15) under them all.
And while one runs and the 1-minute load average is a CPU each or more (`core.CPUFull`), a turn that may wait doesn't start, and the work module starts no waiting brief (`core.Runs.Yielding`, said as `waiting: main's measure`); an executor module with room takes an away turn instead, as with memory.
Turns already running go on, a lead's, warden's or tribunal seat's turn never waits, and with `turn_mb` 0 (tests on a loaded machine) neither hold applies.

## Leads step first

`Runs.Tick` steps the leads first, each on its own goroutine, started in `Run.Nice` order (the Hive-wide lead first) but running side by side, so the order is one of priority, not of who finishes first, and steps the other runs only once every lead's step is done, waiting at most 5 seconds for that on a goroutine of its own, never on the daemon loop; a lead's step still going at 5 seconds is named in `daemon.log`, once a stall: a later tick can't claim the hung lead, so its pass has no lead to wait for and goes at once (`TestHungLeadStepIsSaidOnce`). One such pass waits at a time: ticks that come while it waits step their leads and skip the pass, rather than pile up a waiting goroutine each. The other runs are listed after the wait, as they are then, and each is claimed as it is now (`Runs.claim`), so a tick that overlaps a slow lead step never steps a run from an older view. While a lead's launch is in flight (`Runs.leadLaunching`), a launch of any other role returns at once and is due again next tick, so a lead's turn has its process before a queued worker's or review's starts; a run deferred ten ticks in a row is named in `daemon.log`. The order holds at the start of a launch only: a worker's launch already past that check when a lead's becomes due goes ahead beside it.

## Leads run at a higher priority

Every sandboxed command carries a nice value (`sandbox.Spec.Nice`, from `Run.Nice`): the Hive-wide lead 0, a project's lead 2, every other run 10, and checks and the recursive gate (`hive gate`, which the daemon starts itself) 15 (`core.CheckNice`). A process can only lower its own priority, so each level adds to the daemon's own and is capped at 19 (`sandbox.Lowered`). The bare and Seatbelt sandboxes and the gate prefix `nice -n` through `sandbox.Niced`, which resolves both `nice` and the command on the daemon's own PATH, never on the command's (which carries the tools bins an agent can write to); a relative path with a slash (`./x`) is left as it is, for exec to find from the command's own directory, and Seatbelt runs macOS's own `/usr/bin/sandbox-exec`. With no `nice` on the daemon's PATH a command runs at the daemon's level, said once in `daemon.log`. The Linux launcher (`hive sandbox-exec`) reads its own level and sets the sum with `setpriority` on a thread its goroutine is locked to, since Linux nices a thread and the sandbox is forked from that goroutine later; the init, bubblewrap and the command inherit it, under WSL too. A failed `setpriority` doesn't stop the command; it is said in the run's stderr log (`<stdout>.err`). Linux's autogroups (`kernel.sched_autogroup_enabled`, on by default on desktop distributions) share the cpu between sessions first and weigh nice only inside a session, and the launcher, bubblewrap's `--new-session` and a harness's every shell command (Claude Code's) each start one, so a worker's pytest at nice 10 took as large a share as the person's whole terminal (10-28: load 110-137 on 20 cores). So the launcher gives its own session's autogroup the command's level when it leads that session, and every few seconds (`autogroupEvery`) gives it to each autogroup of a session started under it, read from the sandbox's process tree; it only ever lowers one, and never touches the session it was started in (`internal/sandbox/autogroup_linux.go`, `TestLowerAutogroupsLowersSessionsStartedInside`). Without autogroups the kernel ignores the value and nice alone holds. Only the forked sandbox is lowered: goroutines the launcher starts on other threads (the egress server, the signal loop) keep the daemon's level, so host-side work moved into the launcher would too.
