# Risk: tiers, warden, tribunal, the person

Built in `internal/mod/risk` (spec sections 4, 7 and 15, milestone 6).

## Tiers and routes

A worker asks with `hive agent warden --want --why --steps --tier T1|T2|T3`. `core.Route` picks who settles it:

- **T1** (inside the Hive, recoverable): the worker's own; nothing is filed.
- **T2** (outside but recoverable, or load-bearing inside): a warden. At autonomy 1 the person says yes first; at autonomy 3 the warden settles it and the person is told after: a `person.told` event (`Person.Tell`), shown in the control center's feed and its "done for you" list with what ran, why and the output, never a Waiting item. Waiting holds only what needs their decision.
- **T3** (outside and hard to undo): a warden, which always ends in a tribunal.
- **Always the person** (`core.AlwaysPerson`: money, credentials, opening the machine to the network, outward in their name to other people, such as a mail, a post or a message; merging, releasing or pushing on the person's own repository with the Hive's login is not that, and a warden settles it): straight to the person, at any tier and autonomy. `core.CeilingHit` spots these by keywords and credential-store paths in the text, so it is a best-effort check that errs toward the person: an agent that hides the words (a variable, base64) gets past it. Routing a request reads its words with `core.AskCeilingMatch`, which skips a mention the ask rules out (a negation such as "do not", "no", "without" at most three words before it in the same clause and the only negation there (a second one, as in "won't work without your API key", turns it back), or `listen on` a loopback address; a money mention, a negated cap ("don't expose more than one port") and a local egress grant, and a negated protection such as "no firewall" or "do not block inbound" always count, since they still spend or open the machine), so "do not set OLLAMA_HOST=0.0.0.0" reaches a warden; any other mention still routes to the person, and the ask names the category and the words that matched. The script that would run still meets `core.CeilingGuard`, which counts every mention.
- **The person's floor** (`floor` in `.hive/config.json`, empty by default): names never touched, paths no script writes, secret globs, service roots. A step whose text touches an entry goes to the person the same way, whatever a warden or panel would say (`core.FloorHit`: an entry with `*?[` matches a word or its last path element, any other entry matches as written). It is the same best-effort text check, so write entries as scripts would spell them (`.ssh/`, not `~/.ssh`).

A "gate" Waiting item (landing a change to the gate's own code unjudged while main itself fails in the gate, docs/gate.md) is the person's alone: it is asked straight to them, never through `risk.Weigh`, so no warden or tribunal answers it at any autonomy, and its approval lands only that head at that main.

A decision that would otherwise wait in the person's queue goes the same way through `risk.Weigh`: a merge that changes protected paths (goals, `docs/REVIEW.md`, the score, settings; the ask quotes their diff) and a module install. At autonomy 1, or when the ceiling's words show up, the person decides as before. Otherwise a warden weighs it as T2 and may call a tribunal. No script runs: its `do` or decline answers the person's ask (merge or leave open, install or decline), so the ask's own handler acts, and a "told" item tells the person after. The worker that wrote a change never weighs it and is sent nothing about it, since its turn is over. A warden that ends without deciding hands the ask to the person.

## Warden

An agent (`modules/agents/warden.md`) spawned per request in a scratch directory. The request reaches it as fenced, quoted data, so the worker's words are information, never instructions. It can research, spawn workers and message the requester, then calls `hive agent decide` once: `do` with a script, `safer` with a route the worker takes itself, `decline`, or `tribunal` with a script and a brief (`--gain large` sends a decline on to the person). A warden that messages another agent waits for the reply, as it does for a helper it spawns. It can also pass the step to the person (`person`, with or without a script), the route for a system install that needs root. A warden that ends, goes quiet or runs past `WardenTimeout` (30 minutes) without deciding hands the request to the person too (the clock runs only while the warden can take turns: parked on a usage limit or queued for a slot, it waits, and its 30 minutes count from the later of the request and its latest turn's start), and nothing runs until they answer: in Waiting, with `hive approve` / `hive refuse <id>`, or with `hive answer`. A script that uses `sudo` runs only where `sudo -n` works. Elsewhere a warden's `do` with sudo is refused with the reason, and one a panel approves goes to the person to run themselves. A step runs with no terminal (in a session of its own), so where sudo needs no password for some commands and wants one for others, a sudo that wants one fails at once. A step that fails and printed sudo's password message goes to the person with its output, to finish themselves, and is never re-run; the match is on the text, and a step that succeeds is done whatever it printed. The shell doesn't stop at a failed command, so the lines after that sudo have run too. The brief tells the warden that sandboxes see the host's system directories read-only (there's no separate image), whether sudo can run, and, inside the same fence, how the project's other requests were decided in the last hour. The same want (ignoring case and spacing) asked again in the same project joins the open request, whose answer reaches every asker, or gets the answer of one done or declined within the hour, so one need gets one verdict; a failure answers nobody else, so asking again retries it. The lead sees requests, and how the person answers them, with the `requests` op. The answer always reaches every agent that asked: one that already finished, even blocked, is woken with it and goes on in its checkout.

## Tribunal

Three read-only, isolated runs (`modules/agents/tribunal.md`; no other project and no module in view, only the case) spread over the `tribunal_models` setting, so the panel spans models where the config lists more than one (empty falls back to the main model). A seat is a model name on the project's harness, or `{"harness": ..., "model": ...}` to sit on another; a harness the Hive doesn't have is refused when the config is saved and when a panel convenes. Each gets the step, the script (`script.sh`) and the warden's brief, investigates and votes, as a structured final answer (`VoteSchema`, the way the reviewer gives its verdict, since a read-only turn has no shell); in round 2 each sees the others' votes and reasons and votes again. All of that agent-written text (step, script, brief, others' reasons) sits inside one fence, as in the warden's brief. A vote counts only as exactly one clean structured answer: a second result in the turn's output, a field the schema doesn't name or a wrong type is no vote, which is a decline. A seat that fails to reopen for round 2 three times counts as a decline, so the request still settles. A majority of final votes approves. A decline with a large gain becomes a person ask whose "run" runs that same script.

## Security reads at merge

A PR that touches a path on main's `tests/LANDING-security.toml` doesn't merge on the ordinary reviewer's land alone. The work module's gate (`securityRead`) asks the Hive's own seats for a security read of the change's own diff (`core.DiffID`): first a security seat, a read-only reviewer run on the first `tribunal_models` seat whose model isn't the reviewer's, briefed on the sandbox, credentials and what runs outside it; then, for a path on the list's `root` entries or in the project's root class (which needs both reads whether or not the list names it), a panel of three such runs over the tribunal seats, one round, decided by majority once every seat has read: two lands with a seat still reading don't merge, so each seat's verdict is counted (issue #413: the seat that ended first was passed over by the majority behind it). Each verdict is recorded with the seat the host gave the run, so it never counts as an ordinary read; a head with the same own diff keeps it, and any other needs a new one. `Effects.Merge` refuses without it (`SecurityOK`). Seat tries are counted per own diff, so a diff that moves without a send-back starts its seats fresh. A security seat with no tribunal seat on another model reads on the reviewer's model, and a seat on a harness the Hive doesn't have reads on the reviewer's; each says so in an alert rather than failing the task. A head sent back on a fix recorded for its unchanged own diff is told the fix still stands. The panel is one round of reviewer runs on the own diff, not the risk module's two-round tribunal: it reads code against the reviewer's rules and verdict schema, where the tribunal weighs a script to run on the host, and its fix only sends the change back for another round, so a second round buys little; whether the person wants the full tribunal here is open (#244). A read from the box's perms seat or architect (`hive read`) counts in place of the seats', and its fix sends the change back even over the seats' land: they steer when the Hive goes off track, and aren't needed otherwise.

A draft PR doesn't hold the Hive's merge on its own: once every read above clears its head, `Effects.Merge` readies it (`Forge.ReadyPR`, only at that head; `effect.readied` is journalled only when the forge changed something) and merges at `--match-head-commit`. That includes a draft made outside the Hive with no word on why, since nobody outside reads its PRs any more (the person's word, issue #239); only a draft the lead holds with `pr_draft` (`DraftWhy`), or one whose head moved past the commit read, waits. The lead's `pr_ready` readies a PR without the gate: readying is not a read, and the merge stays gated.

## Root paths at release

The person's word (24 Oct 2026, through the box, on whether a tribunal may release root-path changes instead of them): "Yes. Release them yourself and say so after." So a release of the Hive's own project whose merges touch a root path (what runs with elevated rights) goes out once the Hive's own reads passed each such merge: its ordinary read, and the security read `SecurityOK` asks at merge (the security seat and a majority of the panel on its own diff, or an outside read from the box's perms seat or architect). The release notes name who passed its root paths, and the person gets a "done for you" entry in the feed after it is cut, not a release-or-hold ask in Waiting. Every path in the project's root class gets that read at merge whether or not the security list names it (`ChangeOf` puts it in both `Security` and `SecurityRoot`), and the seats read the merge's whole own diff, so their land passes all of a merge's root paths together; an outside read decides alone, and its fix outweighs the seats' land. A merge with no read, or a root path no security read passed, still holds the release for the person's "release", as does a root path whose merge record has no diff (merged before `effect.merged` carried one), since no read can be matched to it. A merge approved by the person or a warden but never read by the seats holds too: the approval let it merge, not release. Once a release is cut, any open release ask it covers is answered by the Hive.

"A fix that's no worse than what's on main shouldn't wait for a person": a PR whose failing checks all fail on main too merges (`ChecksAgainstMain`), and improve neither reverts nor asks about a merge whose red tests all failed on main before it. Neither the release nor the improve path asks the person only because main is red: a release is cut only after a kept (green) merge, and a red or late gate on a pre-release raises an alert, not an ask.

A host-made revert goes through the same gate: a revert of a merge that touched a listed path waits for the seats' read like any change, with no exemption. The seats are the Hive's own, so nobody's hand is needed, and a wait that lasts reaches the lead through improve's stall watcher.

A clean PR merges as it is onto the newest main (main is merged in only on a conflict, when the forge requires the branch to be up to date, or when the merge fails its tests), but not before the Hive has run the project's tests on the PR merged with that main (`work.mergedTests`, once per head and main): two changes that each merge cleanly and pass alone can still break main together (on 2026-10-25 one added a caller of `EnsureRepo` two minutes before another changed its signature, and main failed vet for 36 minutes). A red merge where main is green is pushed to the branch and goes back to the worker. Known gap: main can still move between that test and the merge itself, and the forge's own CI ran on the PR merged with main at push time; improve measures main after every merge for what slips through.

Known gap: a forge token refused a head's checks (HTTP 403) on a head with no `.github/workflows` reads as having no checks (#464), so the change merges on the Hive's own tests. A repo whose statuses or check runs come from an outside app (CircleCI, Buildkite, a GitHub App) with no workflow file would have them hidden by the refusal; branch protection's required checks still hold the merge at the forge. No project the Hive runs today is set up that way. A head with workflows keeps the refusal as an error, and the stopped task comes back within an hour of the permission being granted.

## The release repository's steward

Only one of the person's Hives merges and releases in `release_repo`: the Hive whose id (`.hive/hive-id`, read-only to every sandbox) is the first word of `.hive/steward` on its main. `Effects.Stewardship` checks the record before every merge and release in that repository, for any project there, not only the self one; a release reads it at main as it is now, not at the tag. A record it can't read refuses: the commit is read in the local clone, falling back to main as last fetched, and only a file that is absent at a readable commit counts as no record. Another Hive works in a fork in the owner named as `self_fork` and offers its changes upstream; the steward itself works in the upstream even with `self_fork` set.

The record is protected, so a change to it is a protected-path merge: the person's word, or at autonomy 2 and above a warden's in their place, as for goals. That is enough here, since only the steward (or, before any record, a Hive that already works in the upstream) can merge in the release repository at all.

Until the record exists, the grandfather path stays open: a Hive that already worked in the upstream before the record (H0) still merges there, and a new one works there only with the person's `steward: true` word on `/api/project`. The steward files the change that writes the record once (a brief "Record this Hive (<id>) as the steward of …"); merging it closes the path. The id is generated (`hive-…`) unless the person writes a name of their own (H0) into `.hive/hive-id` first; a rename while that brief is open raises an alert asking them to stop it, and the claim is filed again under the new name. A Hive that loses `.hive/hive-id` gets a new id and is refused the upstream; writing the old id back, or changing `.hive/steward`, recovers it. Handing stewardship to another Hive is the same: a change to `.hive/steward` naming it.

## Point of effect

`execute` runs in the daemon (the effects process), never in an agent's sandbox:

1. The script must match the sha256 pinned when it was weighed, or it is refused. The pin covers the script's text only, not the files it runs or reads: a script that calls a file an agent can still edit runs whatever that file holds at the time. The warden and tribunal prompts say so, and ask for those lines inline or a fetch pinned by checksum.
2. `core.CeilingGuard` refuses an always-the-person or floor script unless the person said yes, whoever approved it; the step becomes a person ask that keeps the warden's or tribunal's reasoning. It is the same best-effort text check as above, a last check rather than enforcement.
3. The narrow grant: `sh -c <script>` in `.hive/risk/<id>` (Git for Windows' `sh` on Windows), with a 10 minute timeout that kills the script's whole process group (on Windows it ends only `sh`, whose children may outlive it), and only PATH, HOME, USER, LANG and TMPDIR from the daemon's environment, so tokens in that environment never reach the script.
4. The script runs as the daemon's user and can read that user's files, so its output never goes back to the agent: the agent hears only done or failed, and the output is kept on the request for the person. A scratch HOME would not close this, since a script can name the person's home outright, and it would break steps that need the person's own tool logins.

A restart while a step runs marks it failed and doesn't run it again.

A worker that finishes with no commits finishes its task done when every step it asked for ran and succeeded, and the person is told what ran; if any was declined or failed, the task is blocked with each step's state.

## Egress

Every sandboxed run reaches the network only through the Hive's egress proxy, which refuses this machine and private ranges. `egress` in `.hive/config.json` narrows it: `default` is the hosts every run may reach, and `roles.<role>` (warden, tribunal, worker, lead, ...) replaces it for that role; a role set to `[]` reaches only its harness API host. A run's harness API host (`api.anthropic.com` for Claude) is added to any list. A project's checks (tests, builds) are held to `default`, or `roles.check`. With no list a run reaches every public host, as before. So an empty `default` means every public host while an empty role list means the API host only; that asymmetry is deliberate, since an empty `default` is the same as none and a role key set to `[]` is the only way to shut a role in. Bare runs have no proxy, so no egress list holds them; on Windows the list goes into WSL with the rest of the run's spec. A host matches itself and its subdomains. A refused destination is recorded next to the turn's output with why (`unlisted`: off the run's list; `local`: this machine or a private network) and journalled as `run.egress_refused` when the turn ends, with each destination's reason in a line and, for a local one, the grant that would open it; the agent's own 403 says the same. A loopback address or `localhost` named outright is refused as local before any list is consulted, so the record never blames the list for it.

A service on this machine opens only by a local grant: `egress.local`, one loopback `host:port` each (`127.0.0.1:11434`, `[::1]:11434`, or `localhost:11434` for both), set with `hive egress grant <host:port>` and closed with `hive egress revoke`. A grant holds for every sandboxed run and check from its next turn, past any egress list, and the proxy dials that literal address and nothing else, so a name that resolves to loopback, another port or a LAN address stays refused; anything but a loopback address with a port is refused when the config is read. Inside a Linux sandbox (namespaces or bubblewrap) each granted address is also a loopback listener relayed over the egress socket, so a client that never proxies loopback (Go's, Ollama's own) reaches it at the address it already uses (one it can't bind, like `::1` where loopback has no IPv6, is skipped with a line in the turn's stderr, and the run starts anyway); Seatbelt shares the host's loopback, so its profile allows the granted port directly. In WSL, 127.0.0.1 is WSL's own loopback unless its networking is mirrored. An agent asks for a grant as a warden step (`hive egress grant ...`); `egress grant` and `egress.local` are ceiling words under "opens this machine to the network", so the ask goes to the person at any tier and autonomy. Sandboxed runs can't write the config, so the list changes only by the person's hand or an approved step. A config.json the Hive can't fully read, or with a seat or floor glob it can't use, keeps every setting that did read and says what's wrong in `hive doctor`, the control center's alerts and the daemon's start.

A module's harness spec widens egress too: its `api_hosts` go on the list of every run on that harness (and only those) without a `hive egress grant`, so a module update that adds hosts, a program or a login command deserves the same warden read as its install. The spec can't name a path for its program, a login that runs another program, or env that replaces the proxy, `PATH`, `HOME`, `HIVE_*` or a loader variable (`harness.ParseSpec`). Bare and read-only turns on such a harness rest on its own flags (docs/harnesses.md), which the Hive hasn't verified block every write.

A named model's endpoint goes on its own runs' egress list by name; `Config.openHost` keeps a literal private address or `localhost` off it, and a name that resolves to a private address is refused by the proxy, which resolves every listed name and refuses a private answer (`TestEgressRefusesANameThatResolvesPrivate`). The host widens only runs on the open harness (`TestOpenModelTurn`).

A named model's key (docs/models.md) reaches a turn as a file in the run's home, which the open agent (or `hive open-key`, Claude Code's helper) reads and deletes before any tool runs. Two things keep that window closed, and a later change has to keep both: each turn is a pid namespace of its own, so no process an earlier turn left (a detached one included) is alive when the next turn's key is written (`TestTurnEndsItsProcessesBothPaths`); and nothing of the run starts before the agent's first read (Claude Code's hooks are off for those turns, and no Hive hook runs before the harness). Passing the key on an inherited descriptor would close the window altogether, but would have to cross `sandbox-exec`, bwrap and the namespace init. After the read, the key is in the agent's memory while the model's commands run as the same user: the open agent makes itself non-dumpable, so reading it through `/proc/<pid>/mem` or ptrace needs `CAP_SYS_PTRACE`, which a sandboxed command must not hold. That rests on the kernel's ptrace rules and the sandbox's dropped capabilities, so the key is not gone once read. Claude Code on an Anthropic-compatible model isn't non-dumpable, and there it rests on Yama's `ptrace_scope` alone, the same exposure Claude's own token has. The agent's `Unsetenv` doesn't clear `/proc/self/environ`, harmless while no secret is in that environment, which a secret must never be added to. The open agent's tools inherit the sandbox's environment, as the other harnesses' do; it holds no credential.

The recursive gate's children (docs/gate.md) have their own way out: under bubblewrap each side's sandbox has no network of its own, and its only route is the gate's **meter** for that side, a CONNECT proxy outside the sandbox that counts bytes. The meter refuses `localhost` and any address in a private, loopback or link-local range. A name is resolved first and refused if any address it resolves to is private. One limit: when the gate itself runs behind a proxy (`HTTPS_PROXY`, as inside the Hive's own sandbox) and a name does not resolve where the gate runs, the meter passes the name to that proxy and leaves refusing a private destination to it. It does not pin an address, because a proxy with a host list (the Hive's own egress) would refuse an IP literal. On the person's machine, with DNS, every name is resolved and checked before it goes anywhere.

Installing a module stays a fixed `git clone` into `.modules/`, on the install answer of whoever decides it (see above). A module that carries a program starts only after a read-only review run approves its code at the commit checked out, and again after each update. The program runs as the person outside the sandbox, so that review is the trust boundary (see [architecture.md](architecture.md#modules-that-run-a-program)).

## Updates

Everything that grants access lives in two folders covered in every sandbox, `logins/` and `.hive/private/`. A sandbox started by a daemon from before `private/` existed has no cover over it: it mounts all of `.hive` and covers only `logins/` and the old `daemon.json`, so once the new daemon moved a run's home there or wrote its token there, that sandbox could read them. So the first daemon start on the new layout ends every turn still alive from the earlier daemon, with the terminate-then-kill a stop uses, and waits for it to go before it moves anything or publishes its token. Ending the turns rather than waiting them out holds on bwrap, Seatbelt and WSL alike, because every backend starts a turn through the same detached process the stop path kills, while a turn can run for hours and the daemon can't serve without a published token; the runs resume from their sessions on the next tick. A move the daemon can't make (a place already taken keeps what it has, and the old folder goes beside it under `private/`; a Codex home whose place is taken is one ended turn's copy and goes) or a turn it can't end stops the start with the path named, so no agent reads state while a token sits in the readable tree. On macOS the Seatbelt profile holds a home's old path as a string, so a turn that did outlive the update would also lose its writable home; ending them first closes that too.
