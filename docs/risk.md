# Risk: tiers, warden, tribunal, the person

Built in `internal/mod/risk` (spec sections 4, 7 and 15, milestone 6).

## Tiers and routes

Wardens are only for the hard limits (the person, 10-30): money, credentials, publishing private details, opening the machine, anything outward in the person's name, and deleting repos or history. An agent's run reaches all the hive user can: its whole home (`internal/core/home.go`), git and gh on the agents' tokens, and the hive user's service manager (`systemd-run --user`), so everything else it does itself. `hive agent warden` hands any other ask straight back as the agent's own (route `self`), whatever tier it names; one that publishes private details or deletes a repository or history (`core.WardenOnly`, `core.WardenHit`) goes to a warden, a deletion as T3 to a tribunal, and the ceiling's own list goes on to the person. A module install (`install_module`) isn't weighed: it installs at once.

A step on another machine (`ssh host2`, an `ssh://` address, "another machine") goes to the person, who alone reaches it (`internal/mod/risk/reach.go`).
Nothing else is routed by reach: a full host disk, a stale lock in a host clone or a path a sandbox once hid are the agent's own now that its run reaches them.

A worker asks with `hive agent warden --want --why --steps`; the Hive sets the tier from the category, and an asker's `--tier T3` only raises it. For an ask in those categories, `core.Route` picks who settles it:

- **T2** (publishing private details): a warden. At autonomy 1 the person says yes first; at autonomy 3 the warden settles it and the person is told after: a `person.told` event (`Person.Tell`), shown in the control center's feed and its "done for you" list with what ran, why and the output, never a Waiting item. Waiting holds only what needs their decision.
- **T3** (deleting a repository or history): a warden, which always ends in a tribunal.
- **Always the person** (`core.AlwaysPerson`: money, credentials, opening the machine to the network, outward in their name to other people, such as a mail, a post or a message; merging, releasing or pushing on the person's own repository with the Hive's login is not that, and a warden settles it): straight to the person, at any tier and autonomy. `core.CeilingHit` spots these by keywords and credential-store paths in the text, so it is a best-effort check that errs toward the person: an agent that hides the words (a variable, base64) gets past it. Routing a request reads its words with `core.AskCeilingMatch`, which skips a mention the ask rules out (a negation such as "do not", "no", "without" at most three words before it in the same clause and the only negation there (a second one, as in "won't work without your API key", turns it back), or `listen on` a loopback address; a money mention, a negated cap ("don't expose more than one port") and a local egress grant, and a negated protection such as "no firewall" or "do not block inbound" always count, since they still spend or open the machine), so "do not set OLLAMA_HOST=0.0.0.0" reaches a warden; a parenthesis is a clause of its own, so "which the lead can't do (no credentials)" is judged on its "no"; a credential named as a thing (token, API key, credentials, not an act such as rotate or mint) doesn't count when a negation follows it ("fine-grained tokens can't use the Checks API", but not "the API key isn't set", which asks for one) or its sentence quotes a failure (HTTP 4xx, 401/403, forbidden, not accessible, bad credentials), unless its own clause asks for one ("got HTTP 403, give me a token"), since that says what the agent lacks rather than asks for one (#1990); any other mention still routes to the person, and the ask names the category and the words that matched. The script that would run still meets `core.CeilingGuard` (`core.ScriptCeilingMatch`), which counts every mention except one on a whole-line shell comment that the comment rules out by the same rule ("# Scrubbed environment: no tokens"), since a comment never runs; a mention on a line with code, or one a comment asks for, counts. Both skip `gh auth setup-git` and `gh auth status` (unless its line asks for the token with `-t` or `--show-token`), which read, mint or rotate nothing: the first points git at the login gh has, which in a warden's step is the Hive's own (`forgeEnv`), so a push or merge on the person's repository with it is a warden's (#1990: a push went to the person on it).
- **The person's floor** (`floor` in `.hive/config.json`, empty by default): names never touched, paths no script writes, secret globs, service roots. A step whose text touches an entry goes to the person the same way, whatever a warden or panel would say (`core.FloorHit`: an entry with `*?[` matches a word or its last path element, any other entry matches as written). It is the same best-effort text check, so write entries as scripts would spell them (`.ssh/`, not `~/.ssh`).


No merge waits on a decision any more (the person, 10-30: "freely edit everything including the core with no process"): a change to protected paths (goals, `docs/REVIEW.md`, the score, settings, the steward record) merges like any other, with no ask to the person or a warden. `risk.Weigh`, which settled such an ask as a T2 warden step, has no caller in the merge path.

## The way back

What keeps a mistake undoable is outside every agent's reach:
- each repository's `keep-history` ruleset on its default branch refuses a force-push and a deletion, whoever's token pushes. The person's repositories have it, and one the Hive makes gets it as it is made (`core.GitHub.EnsureRepo`). A free plan has no rulesets on a private repository, so a private one has none;
- the agents' tokens hold no administration, so no agent can lift a ruleset or delete a repository;
- a nightly copy of the Hive's own state (`~/hive-backups`);
- the build H0 ran before its last update (`hive agent fallback`).
A bad change is reverted with a new commit.

## Warden

An agent (`modules/agents/warden.md`) spawned per request in a scratch directory. The request reaches it as fenced, quoted data, so the worker's words are information, never instructions. It can research, spawn workers and message the requester, then calls `hive agent decide` once: `do` with a script, `safer` with a route the worker takes itself, `decline`, or `tribunal` with a script and a brief (`--gain large` sends a decline on to the person). A warden that messages another agent waits for the reply, as it does for a helper it spawns. It can also pass the step to the person (`person`, with or without a script), the route for a system install that needs root. A warden that ends, goes quiet or runs past `WardenTimeout` (30 minutes) without deciding hands the request to the person too (the clock runs only while the warden can take turns: parked on a usage limit or queued for a slot, it waits, and its 30 minutes count from the latest of the request, its latest turn's start and the last time it was seen parked or queued; whatever its state, a request it has held for `WardenHoldMax` (a day) goes to the person, and while its warden is parked or queued the `requests` op says so), and nothing runs until they answer: in Waiting, with `hive approve` / `hive refuse <id>`, or with `hive answer`. A script that uses `sudo` runs only where `sudo -n` works. Elsewhere a warden's `do` with sudo is refused with the reason, and one a panel approves goes to the person to run themselves. A step runs with no terminal (in a session of its own), so where sudo needs no password for some commands and wants one for others, a sudo that wants one fails at once. A step that fails and printed sudo's password message goes to the person with its output, to finish themselves, and is never re-run; the match is on the text, and a step that succeeds is done whatever it printed. The shell doesn't stop at a failed command, so the lines after that sudo have run too. The brief tells the warden that sandboxes see the host's system directories read-only (there's no separate image), whether sudo can run, and, inside the same fence, how the project's other requests were decided in the last hour. The same want (ignoring case and spacing) asked again in the same project joins the open request, whose answer reaches every asker, or gets the answer of one done or declined within the hour, so one need gets one verdict; a failure answers nobody else, so asking again retries it. The lead sees requests, and how the person answers them, with the `requests` op. An approved step's output is kept for the person, since a script runs as the daemon's user and can print that user's secrets. A warden that reads a T2 script as read-only (a diagnosis: a measurement, a log, a status) decides `do` with `--share output`, and then the asker gets the output too, redacted line by line before it is clipped. Withheld: a line naming a credential with a value (after `=`, `:` or a space, as `.netrc` writes it), any `NAME=value` line at its start whatever the name, a token in a known shape or any run of 32 or more token characters, a line holding the forge token the script got or a secret-named value from the daemon's own environment, and everything from a `-----BEGIN` line through its `-----END`. Share never goes with `tribunal` or a T3 step: a panel votes on the script and the warden's brief, not on the output going back, so a share there would move the point of effect past the panel's check. The answer always reaches every agent that asked: one that already finished, even blocked, is woken with it and goes on in its checkout.

## Tribunal

Three read-only, isolated runs (`modules/agents/tribunal.md`; no other project and no module in view, only the case) spread over the `tribunal_models` setting, so the panel spans models where the config lists more than one (empty falls back to the main model). A seat is a model name on the project's harness, or `{"harness": ..., "model": ...}` to sit on another; a harness the Hive doesn't have is refused when the config is saved and when a panel convenes. Each gets the step, the script (`script.sh`) and the warden's brief, investigates and votes, as a structured final answer (`VoteSchema`, the way the reviewer gives its verdict, since a read-only turn has no shell); in round 2 each sees the others' votes and reasons and votes again. All of that agent-written text (step, script, brief, others' reasons) sits inside one fence, as in the warden's brief. A vote counts only as exactly one clean structured answer: a second result in the turn's output, a field the schema doesn't name or a wrong type is no vote, which is a decline. A seat that fails to reopen for round 2 three times counts as a decline, so the request still settles. A majority of final votes approves. A decline with a large gain becomes a person ask whose "run" runs that same script.

## Nothing is read at merge

A PR merges as soon as its worker finishes, whatever paths it touches, the core, the sandbox and the security list included: no reviewer, security seat or panel reads it first, and no forge check is waited on (`Effects.Merge` weighs only the person's hold and the steward record). An agent may also push to main itself on its own token. The way back is the measure of main after each merge, which reverts a break, the keep-history ruleset, H0's rule of installing only a main commit whose forge CI passed, and its rollback and fallback builds. `tests/LANDING-security.toml` still names the paths a release reads (below) and, in `required_checks`, the checks H0 needs green before it installs a build of main.

A draft PR doesn't hold the Hive's merge: `Effects.Merge` readies it (`Forge.ReadyPR`, only at that head; `effect.readied` is journalled only when the forge changed something) and merges at `--match-head-commit`. There is no `pr_draft` any more, so no agent holds another's merge with a draft.

## Root paths at release

The person's word (24 Oct 2026, through the box, on whether a tribunal may release root-path changes instead of them): "Yes. Release them yourself and say so after." So a release of the Hive's own project whose merges touch a root path (what runs with elevated rights) goes out once the Hive's own reads passed each such merge: its ordinary read, and the security read `SecurityOK` asks at merge (the security seat and a majority of the panel on its own diff, or an outside read from the box's perms seat or architect). The release notes name who passed its root paths, and the person gets a "done for you" entry in the feed after it is cut, not a release-or-hold ask in Waiting. Every path in the project's root class gets that read at merge whether or not the security list names it (`ChangeOf` puts it in both `Security` and `SecurityRoot`), and the seats read the merge's whole own diff, so their land passes all of a merge's root paths together; an outside read decides alone, and its fix outweighs the seats' land. A merge with no read, or a root path no security read passed, gets that read at release from the Hive's own seats, as at merge (the work module's `ReadMerged`: the ordinary reviewer, or the security seat and then the whole panel, each reading the merge's own diff rebuilt from the host clone and taken only when its `DiffID` is the one the merge record names); the release waits meanwhile (`release.reading`, retried every 10 minutes) and goes out on their land, the person told after. Only a read that can't pass holds it for the person's "release": a seat's or the panel's fix, an outside fix, no usable verdict in three tries, a diff that can't be rebuilt, or a root path whose merge record has no diff (merged before `effect.merged` carried one), since no read can be matched to it; the ask says which. (Person, 27 Oct 2026, on the release at 54555ace that waited on them because #601 and #1082 had merged under the old early-majority panel, before #413 made a merge wait for every seat: "That wait was the Hive's to settle itself.") Once a release is cut, any open release ask it covers is answered by the Hive.


improve neither reverts nor asks about a merge whose red tests all failed on main before it. Neither the release nor the improve path asks the person only because main is red: a release is cut only after a kept (green) merge, and a red or late gate on a pre-release raises an alert, not an ask.

A host-made revert merges at once, like any change.

A clean PR merges as it is onto the newest main (main is merged in only on a conflict, or when the forge requires the branch to be up to date). Two changes that each merge cleanly and pass alone can still break main together (on 2026-10-25 one added a caller of `EnsureRepo` two minutes before another changed its signature, and main failed vet for 36 minutes); improve measures main after every merge and reverts what broke it. The Hive no longer tests each PR merged with main before it merges: that test made a merge line every merge in a project queued through one at a time, where some 50 tasks waited hours (2026-10-27, docs/log.md).

A fine-grained token can't use the Checks API (GitHub offers it no checks permission, so check-runs and check-suites answer 403), so on that 403 `GitHub.Checks` reads the head's Actions runs and their jobs (the same names, states and job URLs) and its commit statuses instead; a head with workflows whose runs aren't listed yet is held for ten minutes from its first read, as a young Actions suite holds it. Known gap: a forge token refused those reads too (HTTP 403) on a head with no `.github/workflows` reads as having no checks (#464), so the change merges on the Hive's own tests. A repo whose statuses or check runs come from an outside app (CircleCI, Buildkite, a GitHub App) with no workflow file would have them hidden by the refusal; branch protection's required checks still hold the merge at the forge. No project the Hive runs today is set up that way. A head with workflows keeps the refusal as an error, and the stopped task comes back within an hour of the permission being granted.

## The release repository's steward

Only one of the person's Hives merges and releases in `release_repo`: the Hive whose id (`.hive/hive-id`, read-only to every sandbox) is the first word of `.hive/steward` on its main. `Effects.Stewardship` checks the record before every merge and release in that repository, for any project there, not only the self one; a release reads it at main as it is now, not at the tag. A record it can't read refuses: the commit is read in the local clone, falling back to main as last fetched, and only a file that is absent at a readable commit counts as no record. Another Hive works in a fork in the owner named as `self_fork` and offers its changes upstream; the steward itself works in the upstream even with `self_fork` set.

A change to the record merges like any other, with no approval; only the steward (or, before any record, a Hive that already works in the upstream) can merge in the release repository at all.

Until the record exists, the grandfather path stays open: a Hive that already worked in the upstream before the record (H0) still merges there, and a new one works there only with the person's `steward: true` word on `/api/project`. The steward files the change that writes the record once (a brief "Record this Hive (<id>) as the steward of …"); merging it closes the path. The id is generated (`hive-…`) unless the person writes a name of their own (H0) into `.hive/hive-id` first; a rename while that brief is open raises an alert asking them to stop it, and the claim is filed again under the new name. A Hive that loses `.hive/hive-id` gets a new id and is refused the upstream; writing the old id back, or changing `.hive/steward`, recovers it. Handing stewardship to another Hive is the same: a change to `.hive/steward` naming it.

## Point of effect

`execute` runs in the daemon (the effects process), never in an agent's sandbox:

1. The script must match the sha256 pinned when it was weighed, or it is refused. The pin covers the script's text only, not the files it runs or reads: a script that calls a file an agent can still edit runs whatever that file holds at the time. The warden and tribunal prompts say so, and ask for those lines inline or a fetch pinned by checksum.
2. `core.CeilingGuard` refuses an always-the-person or floor script unless the person said yes, whoever approved it; the step becomes a person ask that keeps the warden's or tribunal's reasoning. It is the same best-effort text check as above, a last check rather than enforcement. The person's run on a script binds to that script's ceiling lines (`risk.ceilingLines`): each line outside a whole-line comment with a money, credential, network or outward mention or a floor entry, and in a script that spends, each line that loops (for, while, until, xargs, parallel, seq, yes, watch), counted, whitespace collapsed. For `risk.CarryFor` (7 days) a later warden-approved script in the same project carries that run when every one of its ceiling lines is one of those lines, used no more often, or the same line with smaller `$` amounts (`risk.within`): `--budget-usd 5000` against `--budget-usd 25`, the login file sent elsewhere, a second copy of the line or a new loop each go to the person. So a restart or fix that keeps the money, caps and login lines isn't asked again; the run ask says so before the person answers. Only a run on a script the Hive ran carries: a done (the person did it themselves) and the agent's words around a script approve nothing the daemon runs. The request records `carries` (the approved request's id) and `carries_digest` (that script's sha256, its `digest`), checkable against the `risk.saved` records, and the person is told the step ran on their run. A refused script's ask lists its ceiling lines. A run carries nothing once the person has declined a script sharing one of its ceiling lines (or an ask whose words its mentions hold). An ask whose words' mentions a carrying run's script holds goes to a warden rather than the person, at any tier, so it is weighed and recorded; that only routes, and what runs must still be held line by line. It stays a text check: a cap in a file the script calls, or a value passed through a variable set on another line, isn't seen.
3. The narrow grant: `sh -c <script>` in `.hive/risk/<id>` (Git for Windows' `sh` on Windows), with a 10 minute timeout that kills the script's whole process group (on Windows it ends only `sh`, whose children may outlive it), and only PATH, HOME, USER, LANG and TMPDIR from the daemon's environment, so tokens in that environment never reach the script. The one it adds is the forge's own: `GH_TOKEN` for the project's repo owner (`core.ForgeEnv`, the token the Hive pushes and merges with there), so gh and git in a step on an org repo reach it as the Hive does instead of falling back to gh's own login, which may not see it; the warden's brief says which login its script gets. The output, which could print it, goes only to the person.
4. The script runs as the daemon's user and can read that user's files, so its output never goes back to the agent: the agent hears only done or failed, and the output is kept on the request for the person. A scratch HOME would not close this, since a script can name the person's home outright, and it would break steps that need the person's own tool logins.

A restart while a step runs marks it failed and doesn't run it again.

A worker that finishes with no commits finishes its task done when every step it asked for ran and succeeded, and the person is told what ran; if any was declined or failed, the task is blocked with each step's state.

## Egress

Every sandboxed run reaches the network only through the Hive's egress proxy, which refuses this machine (by any of its addresses: loopback, LAN, Tailscale, a public one, read from its interfaces at every dial, with what its hostname resolves to looked up again every few seconds), private ranges (an IPv6 address carrying an IPv4 one, NAT64, 6to4 or Teredo, is judged by that one too), local names (`localhost`, `.local`, `.lan`, `.home.arpa`, `.internal`, `.corp`, Tailscale's `.ts.net`, any single-label name) and names it can't resolve. A known gap: the router's public address, which neither can see from here, is still reachable, so a port it forwards back to this machine is too. `egress` in `.hive/config.json` narrows it: `default` is the hosts every run may reach, and `roles.<role>` (warden, tribunal, worker, lead, ...) replaces it for that role; a role set to `[]` reaches only its harness API host. A run's harness API host (`api.anthropic.com` for Claude) is added to any list. A project's checks (tests, builds) are held to `default`, or `roles.check`. With no list a run reaches every public host, as before. So an empty `default` means every public host while an empty role list means the API host only; that asymmetry is deliberate, since an empty `default` is the same as none and a role key set to `[]` is the only way to shut a role in. Bare runs have no proxy, so no egress list holds them; on Windows the list goes into WSL with the rest of the run's spec. A host matches itself and its subdomains. A refused destination is recorded next to the turn's output with why (`unlisted`: off the run's list; `local`: this machine or a private network) and journalled as `run.egress_refused` when the turn ends, with each destination's reason in a line and, for a local one, the grant that would open it; the agent's own 403 says the same. A local address or local name named outright is refused as local before any list is consulted, so the record never blames the list for it.

A service on this machine opens only by a local grant: `egress.local`, one loopback `host:port` each (`127.0.0.1:11434`, `[::1]:11434`, or `localhost:11434` for both), set with `hive egress grant <host:port>` and closed with `hive egress revoke`. A grant holds for every sandboxed run and check from its next turn, past any egress list, and the proxy dials that literal address and nothing else, so a name that resolves to loopback, another port or a LAN address stays refused; anything but a loopback address with a port is refused when the config is read. Inside a Linux sandbox (namespaces or bubblewrap) each granted address is also a loopback listener relayed over the egress socket, so a client that never proxies loopback (Go's, Ollama's own) reaches it at the address it already uses (one it can't bind, like `::1` where loopback has no IPv6, is skipped with a line in the turn's stderr, and the run starts anyway); Seatbelt shares the host's loopback, so its profile allows the granted port directly. In WSL, 127.0.0.1 is WSL's own loopback unless its networking is mirrored. An agent asks for a grant as a warden step (`hive egress grant ...`); `egress grant` and `egress.local` are ceiling words under "opens this machine to the network", so the ask goes to the person at any tier and autonomy. Sandboxed runs can't write the config, so the list changes only by the person's hand or an approved step. A config.json the Hive can't fully read, or with a seat or floor glob it can't use, keeps every setting that did read and says what's wrong in `hive doctor`, the control center's alerts and the daemon's start.

A host outside this machine opens to one project by a project grant: `egress.projects.<project>`, `host:port` each, set with `hive egress grant <host:port> --project <name>` and closed with `hive egress revoke <host:port> --project <name>` (the project must exist to be granted). It holds for that project's runs and checks (`Run.Project`, a check's project) from their next turn, past any egress list, and for that port only: a hosted MQTT broker (`broker.example.com:8883`) or a LAN device by its literal address (`192.168.1.20:80`). A named grant is resolved at each dial and refused if any answer is private or this machine, so DNS can't turn it into a way onto the LAN; a LAN device is named only by its address, so a local name (`nas.lan`, a single label) is refused when the config is read, as are loopback, `0.0.0.0` and an entry without a port, and a granted address that is one of this machine's own is refused at the dial (`sandbox.OutsideGrant`, `TestEgressOutsideGrant`). It is reached through the proxy with HTTP CONNECT (`HTTPS_PROXY`), as every outside host is; nothing listens for it inside the sandbox. `egress.projects` is a ceiling word beside `egress grant`, so the ask goes to the person. A turn or check handed to another machine (`dispatch`) takes the grant with its spec, so a LAN address there is that machine's LAN.

A module's harness spec widens egress too: its `api_hosts` go on the list of every run on that harness (and only those) without a `hive egress grant`, so a module update that adds hosts, a program or a login command deserves the same warden read as its install. The spec can't name a path for its program, a login that runs another program, or env that replaces the proxy, `PATH`, `HOME`, `HIVE_*` or a loader variable (`harness.ParseSpec`). Bare and read-only turns on such a harness rest on its own flags (docs/harnesses.md), which the Hive hasn't verified block every write.

A named model's endpoint goes on its own runs' egress list by name; `Config.openHost` keeps a literal private address or `localhost` off it, and a name that resolves to a private address is refused by the proxy, which resolves every listed name and refuses a private answer (`TestEgressRefusesANameThatResolvesPrivate`). The host widens only runs on the open harness (`TestOpenModelTurn`).

A named model's key (docs/models.md) reaches a turn as a file in the run's home, which the open agent (or `hive open-key`, Claude Code's helper) reads and deletes before any tool runs. Two things keep that window closed, and a later change has to keep both: each turn is a pid namespace of its own, so no process an earlier turn left (a detached one included) is alive when the next turn's key is written (`TestTurnEndsItsProcessesBothPaths`); and nothing of the run starts before the agent's first read (Claude Code's hooks are off for those turns, and no Hive hook runs before the harness). Passing the key on an inherited descriptor would close the window altogether, but would have to cross `sandbox-exec`, bwrap and the namespace init. After the read, the key is in the agent's memory while the model's commands run as the same user: the open agent makes itself non-dumpable, so reading it through `/proc/<pid>/mem` or ptrace needs `CAP_SYS_PTRACE`, which a sandboxed command must not hold. That rests on the kernel's ptrace rules and the sandbox's dropped capabilities, so the key is not gone once read. Claude Code on an Anthropic-compatible model isn't non-dumpable, and there it rests on Yama's `ptrace_scope` alone, the same exposure Claude's own token has. The agent's `Unsetenv` doesn't clear `/proc/self/environ`, harmless while no secret is in that environment, which a secret must never be added to. The open agent's tools inherit the sandbox's environment, as the other harnesses' do; it holds no credential.


Installing a module stays a fixed `git clone` into `.modules/`, with no one weighing it. A module that carries a program starts at the commit checked out, and again after each update, with no code review first (the person, 10-30): its program runs as the hive user, as every agent's run in home already does (see [architecture.md](architecture.md#modules-that-run-a-program)).

## Updates

Everything that grants access lives in two folders covered in every sandbox, `logins/` and `.hive/private/`. A sandbox started by a daemon from before `private/` existed has no cover over it: it mounts all of `.hive` and covers only `logins/` and the old `daemon.json`, so once the new daemon moved a run's home there or wrote its token there, that sandbox could read them. So the first daemon start on the new layout ends every turn still alive from the earlier daemon, with the terminate-then-kill a stop uses, and waits for it to go before it moves anything or publishes its token. Ending the turns rather than waiting them out holds on bwrap, Seatbelt and WSL alike, because every backend starts a turn through the same detached process the stop path kills, while a turn can run for hours and the daemon can't serve without a published token; the runs resume from their sessions on the next tick. A move the daemon can't make (a place already taken keeps what it has, and the old folder goes beside it under `private/`; a Codex home whose place is taken is one ended turn's copy and goes) or a turn it can't end stops the start with the path named, so no agent reads state while a token sits in the readable tree. On macOS the Seatbelt profile holds a home's old path as a string, so a turn that did outlive the update would also lose its writable home; ending them first closes that too.
