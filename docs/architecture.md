# Architecture

One Go binary, `hive`. A small core plus default modules; the daemon runs both and serves the control center over localhost.

## Packages

| Package | Role |
|---|---|
| `internal/core` | **The core.** Journal (append-only event log), workspace + config, runs (agent turns, park/resume, crash retry, reattach), mailbox ops, effects process (git/forge, commit extraction, gate guarantees), project registry, token source, person queue, ceiling notes. What is and isn't core, its measured size and the order the rest moves out: [core.md](core.md). |

Claude Code (`claude -p --output-format stream-json`), Codex (`codex exec --json`; inside our sandbox with its own off, since its bubblewrap can't nest; bare, in its own read-only or workspace-write sandbox; usage read from its session rollout at turn end), open (`hive open-agent`: any OpenAI-compatible endpoint; [models.md](models.md)), fake (scripted), built in; any other is a `Spec` a module declares in JSON (`provides.harnesses`: program, login, args per turn, env, API hosts, parse rules), loaded from `.modules/` by `harness.UseModules` ([harnesses.md](harnesses.md)). |

| `modules/` | Default module content (orientation + role prompts, manifests), embedded and written to `.modules/` on first run. |
| `internal/demo` | Demo project template (textkit: tests + score). |
| `internal/softlayer`, `cmd/hive-soft` | The soft-layer experiment ([soft-layer.md](soft-layer.md)): arms of the agents module's prompts, installed into sub-Hives by `TestSoftLayer`, and an observer that reads any Hive's journal (runs, who messaged whom, briefs, helpers, asks, merges). Outside the daemon; nothing in the Hive imports it. |

## Folder on disk (`~/hive`)

```
.hive/      events.jsonl, config.json, chats/*.jsonl, scores/*.jsonl,
            runs/<id>/{host,ro,box}, kb/ (git repo of notes; record/ filed from the journal, untracked), gates/, checks/, improve/sweeps/,
            logins/, private/{daemon.json, update.json, runs/<id>/{home,codex,codex-sessions}},
            tools/<python|uv|node|go>/bin (agent-installed runtimes; read-only at /hive/tools, on PATH),
            reports/{sent/*.json, outbox.jsonl, pending.jsonl} (only when sharing is on)
.modules/   agents, chat, kb, improve, system, + installed (each with .hive-source.json)
projects/<name>/             host clone (effects process only)
projects/<name>/.checkouts/  agents' own checkouts (excluded from the clone)
```

Run dir: `host/` (turn output, prompts, stop file; never mounted on its own), `ro/` (system prompt, brief, inputs; mounted read-only at `/hive/run`; `run.created` names each of these over 1 KB in `stored` instead of journaling it again, and replay reads it back from here), `box/` (mailbox + notes; rw at `/hive/box`); its home (rw `$HOME`) is `.hive/private/runs/<id>/home`. Every run but an isolated project's also gets the whole `.hive` read-only at `/hive/state` (`$HIVE_STATE`), so agents read one another's runs, chats and records. What grants access lives in three folders covered there as a whole (an empty tmpfs; a Seatbelt deny on macOS, after which a run's own writable folders are allowed again): `logins/`, `modules/` (module programs' homes and logs) and `private/`, which holds the daemon's token and every run's home and `CODEX_HOME`. Covering folders rather than files means a run made mid-turn, or a `daemon.json` a restart renames into place, is covered too; a file cover is bound to the inode it found. On its first start on this layout the daemon ends the turns the earlier daemon left running (their mounts carry no cover over `private/`), then moves homes and Codex homes from where earlier versions kept them and deletes their turn specs (docs/risk.md, Updates). config.json and daemon.log hold nothing that grants access. A turn's spec, which carries its token, is written to the temp dir. A project shares at one of three levels (docs/sharing.md): shared, private (covered from the rest as an isolated one is, while its runs mount the shared Hive like a shared project's) or isolated; below, "isolated" covers private too except where a run's own view is meant. Also covered is everything an isolated project leaves in the shared Hive: its clone under `/hive/projects`, its runs' folders and chats, its `checks/`, `gates/`, `risk/` and `kb/isolated/` folders, its runs' scratch folders, its scores, and while any project is isolated the whole journal, since one file holds every project's events (`Runs.hideIsolated`); an isolated run sees no other isolated project's notes. No agent outside an isolated project can spawn into it, file work in it, message or list its agents or see it in `status`, and its agents reach no other project (`Runs.Walled`, judged from the core's record of each run) nor create one, whose name, description and goals would land in the shared record. Records from before these folders (old notes, `risk/<id>`, `checks/<id>.log`) move into them on start, and whenever main's history in the knowledge base still holds a note naming an isolated project (checked every start, so a project isolated later or a rebuild cut short is caught next time), that history starts afresh and the filer's old clones go, so the old text can't be read back from git (a clone of the knowledge base made before shares no history with it after). A run or chat that starts mid-turn shows until that agent's next turn, and a bare run (no sandbox) can't cover anything.

Tools: `hive agent install --tool python` runs `hive tools-fetch` in a sandbox of its own that may write `.hive/tools` (network through the egress proxy, held to the asking run's egress list; on Windows inside WSL, so the builds are Linux ones). uv, node and go come from their official downloads, checked against the official sha256 before anything is replaced; python is `uv python install`, which checks its own. The person is told after each install. `--system "<command>"` (root) becomes a person ask with that exact command. On host paths (bare, Seatbelt) the tools folder's bins come first on PATH, so an installed runtime wins over an older one beside hive.

## Data flow: one ask

1. Person → chat → lead run (persistent Claude session, resumed per message; Claude Code compacts it when full, and the lead keeps its journal in its box `notes.md`, which a replacing lead inherits).
2. Lead → `hive agent brief` → `task.saved` (stage `new`). A brief an agent files (`brief` op) that matches an open task no worker has pushed for yet (new, queued or working, not the filer's own) joins it instead of becoming a task (`internal/mod/work/join.go`): a test name (`Test…`, `Benchmark…`, `Fuzz…`) both name in their title or done line (the joined briefs' included), titles sharing at least 80% of their words, or the same named files under titles sharing 30%. Its title, done and known are added to the task's known (in full for the first six joins, a line each after; a working task's worker is messaged them), each join is kept in `Task.Joins` (who, why, what it added; a lead's thread too, which then hears the task's outcomes as the task's own thread does), and each one joined after the issue opened is posted on it as a comment keyed `hive-joined:<task>:<n>`, so a restart edits rather than reposts; `--apart` (or `--apart true`) files it on its own. The aim is read as `File` reads it before matching, so a bad aim or a fix with no failure named is refused rather than joined. A working task whose worker run has ended isn't joined, and a busy task is waited on 2s at most, all of them 4s, since every brief waits on filing meanwhile. The person's asks and the Hive's own briefs (follow-ups, trials, improve) are filed as they come.
3. work.Tick: issue (idempotent by body marker) → worker run `w-<task>` in a fresh checkout at main → worker `finish`.
4. Effects.Extract: `git bundle` made **inside the sandbox**, fetched into the host clone with fsck, must descend from the recorded base → push `hive/<task>` → PR (idempotent by head branch).
5. Effects.RunCheck: tests on the exact sha in a fresh clean clone, sandboxed; command read from **main's** `.hive/project.json`.
6. Small (docs-only, ≤40 lines, no protected or high paths, not a self project) → merge. Else reviewer run (read-only tools, JSON-schema verdict) bound to the sha; a change to a `high` or `root` path in `.hive/project.json` (a self project also always has `core.SelfRoot`/`core.SelfHigh`, see root-paths.md) needs a second land from a separate reviewer run on the same sha.
7. Fix verdict / red tests → same worker, same checkout, bounded rounds (default 3) → stop with PR open. A host-made revert has no worker: its reviewer gets a revert brief, and findings stop it with the PR open.
8. Merge: main moved → the PR merges as it is while the forge says it merges cleanly (`Mergeable` MERGEABLE), since each main merge moves the head past its reads and restarts its checks; before it does, the host merges main into the head in a clean checkout and runs the project's tests on that merge (`work.mergedTests`, once per head and main, `Task.MergedOK`): a pass, or a red main fails as well, lets it merge as it is, and a red where main is green is pushed to the branch, tested again and sent to the worker; otherwise only a conflict, or the forge's rule that the branch be up to date (`MergeState` BEHIND), has the host merge main into the branch (host-made commit; the read carries while the change's own diff is the same) → retest; while the forge is still working it out (UNKNOWN), it waits under a saved `waiting …` reason, so one that never resolves reaches the lead through improve's stall watcher. A hold says so on the PR once per `work.HoldKey` (its reason with the parentheticals, such as the pending check names, left out). A PR whose changed paths match main's `tests/LANDING-security.toml` `paths` (`Change.Security`; `*` within a segment, `**` across; decided by paths alone, never by what the worker wrote) waits first, with one line on the PR, for its security read on its own diff (`Effects.SecurityOK`). The Hive gives it: a security seat (`s-<task>-<diff>-security-<n>`, named by the own diff so a caught-up head finds it reading), a read-only reviewer run on the first `tribunal_models` seat whose model isn't the reviewer's, briefed on the sandbox, credentials and what runs outside it; then, for a file on the list's `root` entries or the project's root class (`Change.SecurityRoot`), a panel of `core.PanelSeats` such runs spread over the tribunal seats, one round, whose majority of lands passes and majority of fixes sends it back. The host sets each run's `seat` input, so a seat's verdict (`Verdict.Seat`) never counts as an ordinary read, nor the other way. An outside read the person records with `hive read <task|#pr> <sha> land|fix --by perms|architect` (`POST /api/read`, the person's token only) counts in their place; its fix, or the seat's, goes back to the worker. Then the forge's own checks on that exact head (GitHub check runs, the newest attempt of each, statuses, and a GitHub Actions suite under 10 minutes old with no jobs listed yet as pending): each name in the list's `required_checks` must have succeeded there (missing, neutral or skipped holds like one still running; with none required, no checks pass); one still running holds; a failure goes back to the worker as a red test does, except one main fails at its head too (`core.ChecksAgainstMain`, used by the gate and again by `Effects.Merge`): a change whose every failure main shares is no worse than main and merges once the rest pass, so the fix for a red main can land, its log naming the checks red on both, a PR comment saying so, and a `main-red` alert raised once. A change to prose alone (`core.ProseOnly`: markdown, reStructuredText or AsciiDoc, none under `testdata`) isn't held by a failed check at all (`core.ChecksBesidesFailures`, in the merge and again in `Effects.Merge`, whose merge event names them as `red_on_prose`): the Hive's own tests already ran whatever reads it on Linux. A failed check with no finished run on main (`work.unanswered`) has its failed jobs re-run once, automatically, before it costs a round; only a second red goes back. Any other red that would go back is re-run once first as well (`Forge.RerunFailed`; both re-runs note `Task.Retried`); a pass on the re-run goes on and journals `forge.flaked`, and a red on a new attempt URL goes back without waiting out `rerunGrace`. Every failed check's failing tests are journaled once per URL, keyed by package (`pkg::TestX`, `core.FailedTestKeys`; `forge.tests_failed`, from the head and from main); the Hive's own test checks name theirs the same way (`Check.Keys`, read from the whole output before it is clipped), and a red one on a task's head or on main (a merge, or main just before one) is a sighting too (`effect.checked`, check `local test`); improve's quarantine (`improve/quarantine.go`) lists a test red in the last 24h on main or on two unrelated tasks' branches (a pass on a re-run is that branch's evidence, never a quarantine alone), files a `Fix the flaky <test>` task for it, and lifts it when that task merges. A PR is judged on evidence from outside its own task (`Effects.Quarantined(project, task)`: none of its own, its follow-ups' or its heads' reds count), and a check shown to fail only in quarantined tests (`core.Excuse` via `Effects.Excused`: the log's failing tests, each placed in its package, all quarantined, and nothing else failing, `core.OnlyTests`; none in a package directory the PR changes; one failed step; no skipped step that main's finished run of it ran, `CheckSteps`) counts as passing in the gate and again in `Effects.Merge` (`quarantined` on `effect.merged`); the Hive's own red test check on the head is excused by the same rules from its whole log (`Effects.ExcusedLocal`, in the testing stage and again in `Effects.Merge`, `quarantined_local` on `effect.merged`), and the dashboard lists the quarantine per project with each fix task. Inside a shared check the failing tests its log names (`Effects.FailingTests`, GitHub Actions job logs, `core.FailedTests`) are compared with main's: a test main's run doesn't fail makes the check the change's again; a log that names none leaves the check name to decide, and the PR comment says a new failure there can't be ruled out. If GitHub's branch rules still refuse the merge (a required check red on both), `Effects.Merge` returns `core.RefusedRed` and the task holds with that reason and one `main-red` alert instead of counting errors toward a stop; one that can't start (startup failure, cancelled, queued over an hour) is the environment's: the change waits and a `main-red` alert is raised once. The own diff is taken with `--binary --full-index`, so two different binary blobs never share a read. In a self project, last of all, for a task aimed at a gain (`Task.Aim` = `gain`; a fix skips it), the recursive gate (`work/selfgate.go`, docs/gate.md): the daemon runs `hive gate` on the exact head against main, as many at once as the machine carries (`max_gates` the ceiling), with no ties allowed, and `Effects.Merge` refuses such a self merge (`MergeRequest.Gain`) without a keep on that head and main: a measured verdict (`gate.judged`) as a judge on another model than the worker's called it (`judge.decided`, docs/judge.md), the numbers being one thing it weighs. `gh pr merge --squash --match-head-commit <sha>`.
9. Checkpoints (scored projects): while a worker runs, a change to its checkout's reflog makes the host extract its newest commit and score it; one that beats the best kept score (or the last checkpoint's, until main is measured) by more than the tolerance goes through steps 4-8 as a checkpoint on `hive/<task>[-n]`, its PR not closing the issue. Red tests, a fix verdict, a conflict or a "leave open" drop it with the worker untouched. Once merged, the task's base moves to that commit and the worker is told at its next prompt; later commits are laid onto main with that commit as the merge base (`UpdateBranch`, `git merge-tree --merge-base`), since main holds it squashed. A finish with nothing past the last checkpoint is done. Each merged checkpoint keeps its PR on the task (`Banks`), so a revert of it names that PR. A commit is weighed once; a worker sent back after its finish, or whose checkpoint the person left open, gets no more checkpoints. A worker that rewinds past a merged checkpoint is told to bring it back. The merge base needs git 2.40 or later; on an older git it's an error, not a conflict.
10. improve: measure merge sha (tests + score) — unless a main commit already measured contains it (a PR that landed before its task closed): then only `score.covered` names that commit and whether it was kept or red, with no score, alert or revert; measurements are taken to be in main's order, so a merge that comes back late (held for a missing tool, requeued after a failed sync) is covered by a later measurement even when that one is red, and the digest's `red` mark is what says the red may be its — compare with best kept; a score past its tolerance with green tests after a clear fix → kept, re-based, and a brief to look into the dip (issue #568); after anything else → a judge on another model than the worker's weighs it with the change (docs/judge.md), and its keep moves the baseline there; worse → revert task (host-made revert + lessons line) → PR → merge; original PR commented. Red tests are read from the full check log for the failing packages, tests and assertions (that line is the note and the lesson), and what failed runs once more (`retest`: only the failing tests and packages under the project's go test flags): a pass is a flake, so the merge is kept, a `flaky` alert raised and the test filed as work. Still red, but every failing test also failed within 72h at a commit without the change (checked before the merge, none of the task's heads or checkpoints), is a flake too → `flake` alert, no revert.
11. release (self projects, one at a time per project): on a kept merge, list the merges after the one the last release was cut at, up to this one, with the reviewer runs that read each exact head; a merge a newer release already covers is refused with an alert; unless the person said "release", main's own checks (CI) on the kept commit must have passed (`ChecksState` with main's `required_checks`) before it is cut or offered: a failure alerts once (`release.ci_failed`); one still running, that can't start or can't be read journals `release.ci_waiting`; the tick tries the newest such commit, failed or waiting, again every 10 minutes (`retryWaiting`, a wait raised once after 6h) until it passes (`release.ci_passed`), so a re-run that passes releases it, and the next kept merge covers it too; meanwhile, the newest of the 10 merges after it whose checks passed is cut instead (`greenAfter`), covering the waiting one, so a commit whose ci run GitHub cancelled (no check runs, read as pending forever) never stalls releases; ci.yml gives each push to main its own concurrency group by commit, since GitHub cancels the older pending run in a shared group whatever `cancel-in-progress` says; a stewardship or `merges` refusal is alerted once per commit, however often it is retried; a head with no read, or a change to a `root` path that no security read passed (`SecurityOK` on its own diff: the security seat and a majority of the panel, or an outside read), waits for the person's "release"; a root change those reads passed is released and the person is told after (`person.told`), and the cut answers any open release ask it covers; the person's "release" is approval kind `release`, kept apart from a `merge` approval of the same sha, and a newer hold supersedes the older ask; the identity and secret scan (`internal/mod/scan`: the commit's files that its `.hive/public.txt` names, against the deny and handle lists in `.hive/private/scan-deny.txt` and `scan-handles.txt`; any key, deny word or handle blocks with an alert, once per commit and finding, that names file, line and kind only; no handle list blocks with one standing `scan_handles` ask to the person instead, whose done retries the held commit and which a scan that reads a list answers); dry run; release with that list in its notes, as a pre-release, numbered on from the newest release (a pre-release included). The release module's tick (`Publish`, every 10 minutes) makes it the latest, which installs and auto-update follow, once `ci` and `update` pass in its own release runs on its commit; the newest of the waiting pre-releases that passed wins and older ones stay pre-releases; a failed run raises one alert and leaves it a pre-release (a re-run that passes publishes it); a failed `release` run (release.yml: scan, build, sign) is named as the cause instead, since no gate had binaries, and while the newest release's release run stays failed, a commit that changes nothing its failed job reads (scan: release.yml, `.hive/public.txt`, the scan's code, since the daemon's own scan passed at that commit; build, sign or none named: release.yml, go.mod/go.sum, non-test Go) is not cut (`release.held` once per tag, an alert and a `release` ask on each such kept merge); a commit that changes one, a passing re-run, or the person's "release" lets the cut go on; one waiting over 6h is raised once. Right after the cut and again before publishing, the tag's commit is read (`TagCommit`, `commits/refs/tags/<tag>` on GitHub); a tag at another commit (made outside the Hive) journals `release.refused` and alerts. The release stays a pre-release, its merges wait for the next one, and the alert tells the person to reject that tag's release-signing run, since the pre-release already started release.yml there, and then delete the release and its tag. A tag that can't be read at the cut is alerted and recorded as `tag_unread` in `hive.released`, and Publish waits until it reads.
12. Stalls (`improve/stalls.go`, every tick): a task stage, or a run no task owns (warden, tribunal seat, helper), that has gone longer without moving than `max(stall_floor_seconds, 3 × p90 of that stage's recent durations here)` gets its hung turn interrupted once (the core retries it on the same checkout), then is handed to the lead. Moving means the stage changed or the run started a turn or wrote output; parked, quiet and waiting runs and person-waiting tasks are left alone. Each decision is a `stall.saved` event with the limit and sample count, listed in the sweep's digest, and one `alert.raised` per thing, keyed so it updates in place.

## Modules that run a program

A module's `module.json` may name a program and the hooks it serves, so a door (a chat service, mail), voice or a resource lease can be added on top of the released binary instead of a fork of it:

```json
{"name": "door", "exec": ["./door", "--quiet"], "hooks": ["source", "channel"]}
```

The program can be in any language. The daemon starts it from the module's folder (a first word starting with `.` is relative to it) and keeps it running: one that exits is started again after a pause that doubles from a second up to five minutes, and resets once it has run a minute. Its output goes to `.hive/modules/<name>/module.log`. The daemon journals `module.started`, `module.exited` and whatever the module reports. Built-in modules stay in-process; the tick list is the registry's (`Registry.Builtin`), and the runner is one entry on it.

A manifest's `"schedule": {"<job>": "every 4h"}` names jobs the program serves, with their default schedules (config.json's `schedules` override them, and the control center lists and runs them like any job); a due one is journaled as `module.scheduled` (`module`, `job`), a workspace notice every module reads, so a schedule reaches a program the same way a hook does. A program started with `go run` (the kb module's `dream/`, standard library only, since a module folder has no go.mod) builds into the person's own Go build cache (`GOCACHE`, else the user cache dir), not a fresh one under its HOME.

**The module calls the API; the daemon never calls the module.** Each start gets a fresh random token in `HIVE_MODULE_TOKEN`, with the API's address in `HIVE_API`. The daemon keeps the token in memory only, and it dies with the process. A request with a module's token reaches only the endpoints its hooks name, and anything else gets 403. Its token also reaches only the projects the person granted the module (`.hive-source.json` `projects`, set from the Modules screen): an ask, a chat, a run or a task in another project is refused, `/api/events` leaves out their events, and anything with no project, such as the lead's chat, the person's asks and the lead's runs, needs a grant of `*`. The only project-less events every module reads are the workspace notices: `hive.idle`, `hive.started`, `hive.stopped`, `alert.raised` and `module.*`. A module's chat posts are tagged with its name, and the lead reads them as `Module <name>: …`. The registry is the one list of which modules exist, what they serve and which projects they reach. Hooks are read off the journal (`/api/events?after=<seq>`), so a module that was down catches up from where it left off and the daemon never waits on a module. A module's read returns the first 2000 events after its cursor, so catching up never skips a gap. Calls the other way would mean the daemon blocking on a slow program, a second listener per module and a second protocol. A token must come as `Authorization: Bearer <token>`; any other form is refused.

| Hook | What it is for | API it may call |
|---|---|---|
| `source` | asks arrive from outside | `POST /api/ask`; the task's `from` is `<module>/<from it gave>`, so an ask carries where it came from |
| `channel` | the lead's conversation and run notices out; steer and stop lines in | `/api/chat` (read and post), `/api/events`, `/api/run/stop`, `/api/task/stop` |
| `after` | a step after a run or a merge ends | `/api/events` (`run.turn_ended`, `effect.merged`) |
| `status` | read the journal's events | `/api/events` |
| `idle` | act when nothing is running | `/api/events` (`hive.idle`, journaled when the last running or queued run ends) |
| `kb` | consolidate the knowledge base (the kb module's dream) | `GET /api/kb/notes` (the shared notes, practice and digests, the shipped practice docs, the hidden projects), `POST /api/kb/dream` (a pass: files to write or remove, each with the hash of what it read, checked like a filer's commit and committed at once; journaled as `kb.dreamed`) |
| (every module) | | `/api/ping`, `POST /api/module/report` (journaled as `module.reported`) |

**Trust.** A module's program is not sandboxed: a door needs the network and the API on localhost, and a lease needs devices. It runs as the person, so it can read anything the person can, including `.hive/daemon.json` (which holds the person's own API token) and the person's `gh` and `ssh` config on disk. The review gate below is therefore the trust boundary. The scoped token and the scrubbed environment only keep a well-behaved module to its hooks; they don't stop a hostile one. A module installed from git is cloned only on the person's "install", and its program starts only once a read-only review run (`module-reviewer`, scratch copy of its files, structured `approve`/`decline`) has read it at the commit checked out, and the brief names that commit. An update moves the commit, so it stops and is read again before it runs. A decline raises an alert and the program stays stopped. A review that ends with no vote (it failed or crashed) is not a decline: it runs again, up to three times in one life of the daemon, then raises one alert and waits until the person presses `r` on the module in the Modules screen (`/api/module/review`) or restarts the Hive. A clone whose install failed is removed, and a folder with `.git` but no source record is read like any other git module. A module the person put in `.modules/` by hand, with no `.git`, runs as it is, and so does a shipped module (the kb module's `dream/`): its trust comes from the Hive's own merge, where `tests/LANDING-security.toml` puts every `modules/*/module.json` and the shipped program's source behind a security read. The program never holds the forge credential: its environment drops forge and model tokens and the person's config folders, `HOME` is its own `.hive/modules/<name>/` (covered in every agent's `/hive/state`, so no run reads its login or log), and no scope pushes, merges or reads secrets, so effects stays the only holder.

**Against an in-process hook table.** The other way to build this is a hook table: the loop loads each listed module's file by path and calls its hooks in its own process, a door's hooks come from the registry, and a run gets only the modules its row grants. Each credentialed relay stays in the effects process as a verb with a checked shape. The Hive keeps two parts of that: the registry is the only list (the tick list and the grants both come from it), and the credential never leaves effects. It parts ways on who calls whom. An in-process hook table means every module is trusted code in the daemon, written in its language. Here a module can be any program, so the daemon can't call into it safely or cheaply. Instead the module pulls a scoped slice of the API and reads the journal, and a slow or dead module never holds the daemon up. Built-in modules still run in-process, as a hook table would.

## Invariants (enforced by structure)

- A module program's environment carries no credential, and its token reaches only its hooks' endpoints; its review, not the token, keeps it from the person's files.
- Agents hold no credentials. Sandbox gets `CLAUDE_CODE_OAUTH_TOKEN` = short-lived access token only, read fresh per turn; each Codex turn gets a fresh `CODEX_HOME` made on the host side (`private/runs/<id>/codex`, mounted at `/hive/codex`), so nothing the agent planted steers the write; its `auth.json` holds the access token with the refresh token blanked and its `config.toml` the Hive's instructions (argv has a size cap). At turn end it is deleted except `sessions/`, kept in `private/runs/<id>/codex-sessions` for resume; folders the agent locked are opened first, a removal that still fails blocks the run, and daemon start deletes any left by a crash before a turn began. A bare run whose machine login has no readable credential file gets no token, so the harness's own host login works. Each turn goes on the least-used login of the pool (by the fullest of its usage windows still running, `Plan.Used`; the machine's own plus `.hive/logins/<harness>/<name>` from `hive login add`, which refuses a Codex API-key login since it has no access token to hand a turn) not parked at its usage limit, nor at 95% of its weekly window (`WeeklyStop`, the person's ask of 10-25) or 90% of its five-hour one (`FiveHourStop`, 10-26: the rest is left to the person): a login stops taking turns there until that window resets, `Plan.ParkedUntil`; with every login of a pick there, its runs wait for the first reset, and `hive status` and the control center say the login is paused. Below the week's ceiling sits a reserve (`CheckReserve`, issue #983): every other role stops at 90% of a login's week, and only the checks and the leads (`Reserved`: reviewer, security, warden, tribunal, judge, lead) run on to 95%, so a change already written is still read, judged and merged. 95% stays everyone's ceiling: the last 5% is the person's, as is the five-hour window's last tenth, which has no reserve. The host's own logins are renewed by the daemon (`Tokens.Watch`, every minute) in their last minutes (Claude Code renews only within five of the expiry, Codex only once the token is turned away): the harness is found by absolute path (PATH, then `~/.local/bin` and the other usual folders, since a service's PATH lacks them), and a renewal counts only if it exits 0 and the expiry moves. Its harness is also tried hourly with `--version`, so one that can't run is told hours ahead. Every failure is a `login.renew_failed` event and a daemon.log line, backs off 1 to 15 minutes, and the first of a run raises one alert (ref `login:<key>`) and a `login` ask with what to run; a later success, or an expiry that moves past the one it failed at (renewed by hand), replaces the alert and closes the ask. A restart reads an unresolved failure and its count back from the journal, so it isn't told afresh. A renewal turned away by the plan's usage limit (`harness.LooksLimited` on its output) is no failure: logging in again wouldn't change it, so it raises no alert or ask (and closes one an earlier failure left open); it is one `login.limited` event and the login is parked until the reset the harness names (`harness.LimitResets`, an hour when it names none), across a restart too. Only harnesses some route uses are watched (`Config.Uses`); a harness binary inside `.hive/` or `projects/`, which runs can write, is refused, and the harness's output is scrubbed of token-shaped strings before it reaches the journal. The control center lists each login's expiry and last renewal.
- Host git never runs in an agent's checkout (only in host clones and fresh gate clones; hooks disabled, fsck on fetch).
- Only `hive/*` branches are pushed; main changes only by merge; `PushInitial` only into an empty repo with a host-made commit.
- Merge requires: host-recorded passing test on that sha (or a red one whose every failure main's own recorded run at the merge's main shares, `core.NoWorse`, as the testing stage lets on) + (small | land verdict from a core-started read-only reviewer on that sha's own diff | host-made revert/setup) + an approval if protected paths changed (the person's at autonomy 1, else a warden's; `risk.Weigh`) + each of main's `required_checks` succeeded and no forge check failing, can't-start or running on that sha + for a path on `tests/LANDING-security.toml`, a security read that said land on its own diff (the Hive's security seat, with its panel's majority for a root path, or an outside read from perms or the architect, whose fix outweighs any land). A read is bound to the diff its reviewer was given (`core.DiffID`: the change's own diff from its merge base with main, `--binary --full-index`, hunk positions and text files' blob-id lines left out; a binary file keeps its index line, since its delta is relative to the old blob), so it carries to a head with main merged in only while that own diff is unchanged; a merge whose conflict resolution touches the change's own files needs a new read. Any `.gitattributes` is high class, since it picks merge drivers. A high class needs two land runs since the last fix.
- Files the sandbox can write are read with `SafeRead` (no symlinks, same-file check); the host decides what to kill/clean from its own records.
- Nothing an agent requests runs outside the sandbox, except a script a warden or tribunal approved, run by the risk module in the daemon as exactly that digest-pinned script text (the pin covers the text, not files it calls); what is always the person's goes to the person (see [risk.md](risk.md)).
- Every state change is a journal event; restart = replay + reconcile; issue/PR/run creation is idempotent.
- One daemon per workspace: `hive daemon` takes an exclusive lock on `.hive/private/daemon.lock` (flock; LockFileEx on Windows) before it touches anything, and a second one exits, naming the pid, start and starter written there (`daemon.AlreadyRunning`), whatever started it: as soon as a daemon there answers, or after 30s. A holder that doesn't answer is on its way out (ping fails once shutdown begins) or still starting, so a plain start waits for its lock, and says in daemon.log which pid it waits on after 2s; a lock file it can't open names the file's owner (another user's launcher made it first). A command that finds no daemon has the Hive's user unit start one when it serves the workspace (matched on the cleaned, symlink-resolved `HIVE_HOME`), and starts one itself if the unit hasn't taken the lock within 8s (failed, at its start limit, or naming a moved binary). A daemon that starts beside the unit removes a leftover `hive.desktop`. A turn claim another daemon holds is journalled once per daemon as an `alert.raised` (ref `turn-claim`), and a turn started again after a daemon died mid-launch as one too. An update's restart (`--wait-for`) waits up to 20s for the daemon it replaces to let go; a hand-off to systemd or to a renamed binary lets go first.
- One launcher: a command that finds no daemon waits for one that holds the lock but hasn't written `daemon.json` yet, and when the Hive's systemd user unit serves the workspace it has systemd start the unit instead of a detached daemon beside it; enabling the unit removes a desktop autostart left from a start without systemd.
- One process per turn: before a turn starts, the daemon claims it in `runs/<id>/host/turn.claim` (its pid and start, the turn, then the turn's process) under a lock on `turn.lock`; a claim for that turn or a later one by another live daemon makes it back off, and a dead daemon's claim is taken over only once the turn it started has ended (`core/claim.go`). Nor does a daemon start a run's next turn while its own last turn's process runs (alert ref `turn-live-<id>`): a `run.status` to idle or queued doesn't take a running run off running, so a second reopen 2 s after the first (a fix round sent twice, issue #1022) only queues its message; if the turn then finishes done, it ends idle with the finish cleared and the next turn hands the message over. A reopen with the text the running turn was handed, or already has waiting, does nothing: that turn is working on it, so its finish ends the run (issue #1157; `Run.Given`).

## Left alone on a shared machine

Settings in `.hive/config.json`; none of them stops or parks work.

- Leads come first (issue #421, [priority.md](priority.md)): a lead's turn is never held by pressure or `mem_floor_mb`, only under 256 MB available; each tick steps the leads before the other runs, and every run's processes are niced by role, the Hive-wide lead highest.
- `max_output_tokens` (16000): sets `CLAUDE_CODE_MAX_OUTPUT_TOKENS` on each Claude turn, because a spend budget is checked only between turns and one reply can otherwise run long. 0 leaves Claude's own default.
- `monthly_usd` (off): each turn's `cost_usd` is already in its `run.turn_ended` event; the runs fold it into a total per UTC month. Past the figure, the person is told once that month in the feed (`Person.Tell`, id `spend-YYYY-MM`) by `stats.SpendNotice` on the module tick list (the core keeps the total, `Runs.Spent`).
- `mem_floor_mb` (1024), `mem_pressure_max` (10), `cpu_pressure_max` (40): before a turn starts, Linux's `MemAvailable` and memory and CPU pressure (`/proc/pressure/memory` and `cpu`, some avg10) are read. Past any limit the run waits (a lead only under 256 MB available, [priority.md](priority.md)), keeping its status, backoff and nudges, with the reason shown in the control center (`run.held`), and starts on the first tick after the machine recovers. Where those files don't exist (macOS, Windows) nothing is held; 0 turns a check off.
- `max_workers` (0, no ceiling), `load_max` (1): a filed brief becomes an issue and then waits as `queued` (`internal/mod/work/queue.go`). Each tick starts the queued briefs in order (the lead's `queue --now` first, then quick briefs, then its `queue --order`, then as filed), only while fewer tasks are working than the pace allows (below), the machine isn't strained (the three limits above) and, past the pace's start (`max_workers` or 4), its 1-minute load per core is at most `load_max` (issue #850: load alone, mostly child Hives' and builds', held every start on 10-25). A brief naming a file (a path that exists in the project) that a brief being worked on or ahead of it in line names too, or that the working one's worker has changed in its checkout (#406: the checkout read as files, never with git there, against the base's tree read once with `git ls-tree` in the project's clone; cached by the file's stamp, and nothing held or kept while that tree can't be read), waits until that worker is done: a file is only itself (two files of one package start together), a directory is never an area (#399: a brief names its package to say where it works), a `merge=union` file (`.gitattributes`) is no area, and a task past working (landing, testing, reviewing, merging) holds nothing back, since a later conflict goes back to its worker with main, and neither does a brief that itself waits on an overlap (#493: waits never chain, so two briefs never wait on each other); such a brief keeps when its wait on others' files began (`Task.FilesSince`), shown on the dashboard and in `queue` once it passes an hour, and past 4 hours the lead is told once (#701: a broad brief passed by later ones on its other files doesn't starve unseen); a brief the lead moves in line (`queue --order` or `--now`) reads "moved in line" until the next tick weighs it, so the reply never shows the old line's wait; `queue --hold` keeps one back; `queue --now <id> --why` starts one past that overlap (journaled with the reason, still within the caps). A quick brief, one that names a `.md` file under `modules/` and no other path (a merge=union doc aside: a package, a directory, a code file or one still to be made makes it ordinary), is a prompt change: it goes first in line and may start past the pace while no other quick brief is working, unless the workers' plan is nearly spent; it still waits on an overlap and a strained machine (unit `TestQueueQuickPromptBriefs`). `landed --task <id> --why [--merge sha]` (any lead, worker or sweep on its own project, like `queue` and `recheck`; `work.reach`) ends a task in any stage as merged when its PR is MERGED on the forge or main holds its head (squashed: the named main commit must hold it, `merge-tree` adding nothing), recording the merge and running `OnMerged`, so what waits behind it starts (`internal/mod/work/landed.go`). Without the lead, a task whose head brings nothing main lacks (`merge-tree` adds nothing: its work landed through another task, or its branch caught up to main's tree) ends on its own when it next meets main (testing, merging, landing, or its worker finishing blocked): its PR and issue are closed with a comment naming the main commit that brought the work, and it goes to `done` with no further round and nothing measured. One whose own PR is MERGED on the forge is left to the merge path, which records it as merged (or banks a checkpoint) and runs `OnMerged`. Each waiting brief shows why. Nothing here stops a started worker, and a lower cap only holds new starts. 0 turns a limit off.
- The pace (`internal/mod/work/pace.go`): how many workers and checks go at once sets itself. It starts at `max_workers` (or 4) and `max_checks` (or cores/6, at least 2); while something waits on it and nothing has strained for 5 minutes (nor has it changed) it grows by one (for workers, only while a brief waits on the limit itself: one held, or waiting on another's files, doesn't count, as it would leave the new slot empty); when the machine is strained (the memory floor, memory or CPU pressure, load per core over `load_max`) or, for workers, the least used login of every model on the worker routes (the workspace's and each project's own) has under 10% of its plan left (`Runs.Headroom`) or every one is spending its five-hour or weekly window more than 15% ahead of the clock (`Runs.Ahead`: use beyond the share of the window passed, each against its own length, so neither runs out before its reset and leaves the Hive idle), it pulls back to three quarters of what runs, at most once a minute, but load per core alone never pulls the workers' limit under its start, and brings it back up to its start once no other strain (nor the plan) has shown for 5 minutes, nor holds a brief from starting while fewer than the start work, nor hides the plan, which still pulls workers under it (issue #850: on 10-25 the load was child Hives' and builds', not the 2-3 live turns', and the limit swung 30-55 times an hour between 1 and 5 with 51 tasks waiting; the checks' and gates' limits do go under their start for load alone, as their builds and child Hives are what load the machine; `core.LoadedReason` is how load alone is told from the other strains); with nothing running it keeps its limit, at most its start. Nothing running is stopped. `max_workers` and `max_checks`, when set, are the person's ceilings (0: none); a new one starts the pace there. With none set, a safety ceiling holds while the steps are untuned: one worker a core (at least 4), and twice the checks' start. A config from before the pace (no `ceilings` key) saved the then defaults, `max_workers` 4 and `max_checks` cores/6; reading it clears those two values, so the pace grows there too. Each change past the first read is journaled as `pace.changed` (`limit` workers, checks or gates; `from`, `to`, `why`), for a sweep to tune the steps against. With every machine reading off, or none there to read (no /proc, as on macOS or Windows; `core.Watched`), it stays at its start, as it can't see. The limit and why show on the dashboard (agents and checks headings) and in `hive agent status`; it lives in memory, and a restart starts from what already runs.
- `max_checks` (0, no ceiling; the pace starts at cores/6, at least 2, 3 on 20 cores): the gate's test, score and dry-run checks and improve's measures (`Effects.RunCheck`) take a slot first (`core.Slots`); the rest wait in the order they asked, except that the work module ranks them (`Slots.Prioritize`): a check of a task queued briefs wait on goes first, then a fix's (issue #838), shown under **checks** in the control center and in `hive agent status`. The stall watcher times a check from when it got its slot. The pace sets the number of slots (`Slots.Resize`).
- `check_cache_max_mb` (8192): checks have room (`core/disk.go`). A check's home is `.hive/cache/homes/home-*`, its own and removed after, and holds its `TMPDIR` (`/hive/home/tmp`; the sandbox's `/tmp` is memory); a synchronous sandboxed command (a check) dies with the daemon (Pdeathsig, as the unit keeps children across restarts for agents' turns) and whatever it left running in its process group ends when it returns; past this cap its stop file ends it as can't-run. A Go project's check (on a Linux sandbox with its own paths) gets `.hive/cache/gomod` read-only at `/hive/gomod` with `GOMODCACHE`, `GOPROXY=off` and `GOFLAGS=-mod=readonly`, filled by the effects process with `go mod download` (`GOTOOLCHAIN=local`, `GOVCS=*:off`, `GOWORK=off`, no code of the commit's run) once per go.mod+go.sum (`.hive/cache/gomod-sums/<hash>`); a prefetch that fails leaves the check to fetch its own, as before. The build cache is shared only from main (`goBuild`): a check of a commit on main's first-parent line writes `.hive/cache/gobuild/<project>` (mounted read-write at `/hive/gobuild`, plain `GOCACHE`); a check of any other commit gets it read-only and reads it through `GOCACHEPROG=/hive/bin/hive gocacheprog /hive/gobuild /hive/home/gobuild` (`internal/gocache`), which serves main's entries and keeps what this check builds in its own home, so no commit's check can plant outputs another trusts. Before either, the clean checkout's tracked files and folders get times derived from their git object IDs (`stableTimes`), since go reuses a passed test only when every file it opened has the size and time it had: a check reuses every package build and passed test main's checks already made for the same code. A check that fails mentioning `GOCACHEPROG` runs once more without the shared build cache; the hourly sweep empties a project's build cache past 10 GB while no check uses it. A check whose output says the disk or a quota is full (`disk quota exceeded`, `no space left on device`, ENOSPC, EDQUOT) is can't-run, with one `disk` alert naming what uses the room until a check runs again, and it starts the `hive.clean` job (hourly and at start): agents' checkouts whose run ended and whose task is merged or done (stopped or blocked ones after 7 days; reviewers', and runs with no task, after 24 hours; leads' after 7 days), check homes this daemon isn't running (at once: only one daemon runs on a workspace, and the home's stop file is written first, which ends a check a dead daemon left), clean checkouts and prefetch folders over 3 hours old, dead sandboxes' runtime folders in `/dev/shm` (a live `sandbox-exec` holds a lock in its own) and specs no sandbox read in an hour, recursive gate runs a dead gate left untidy (`gate.Reap`, never the one in flight), the module cache past 20 GB while no check runs; then it measures the Hive's disk use and the room on the workspace's and temp filesystems for the dashboard (`State.Disk`). A task's checkouts also go the moment it is merged or done.

## Sandbox (Linux / WSL)

Outer (`sandbox-exec`, host side): egress proxy on a unix socket in `/dev/shm`, stop-file watcher, starts init with `CLONE_NEWUSER|NEWNS|NEWPID|NEWNET|NEWIPC|NEWUTS` (uid 0 → person's uid). Init (pid 1): tmpfs root; binds `/usr /bin /lib* /etc /opt /var /srv` read-only (nosuid, nodev, locked flags kept); fresh `/proc`, `/tmp`, minimal `/dev`; the install of each host `python3`/`python`/`node`/`uv`/`go` that lives elsewhere, read-only at its own path (its install dir if it has a `lib/` beside `bin`, else the bin alone; never the home, a dot-dir right under it such as `~/.local` or `~/.cargo`, a dir holding the workspace, one of its covered folders (`Spec.Guard`, `Workspace.Guarded`) or a mount's host path (a python at /data/bin with the workspace under /data is bound as its bin alone), nor one inside a covered folder (`Spec.Cover`, `Workspace.Covered`, the same list the run spec hides, and every hidden mount); nothing at all when HOME is unset or can't be resolved, the spec has no guard, or a guarded or covered path is relative), with its dir on PATH after the `/hive/` dirs; run mounts; tools at `/hive/bin` (one already on the inside PATH under a system dir, like a Node launcher, runs in place); `pivot_root`; root remounted ro; `lo` up; forwarder 127.0.0.1:3128 → egress socket, and one per granted local address (`egress.local`) that relays a CONNECT to it over the same socket. Command runs in a nested user namespace (no caps); init reaps every orphan reparented to it while it waits for the command, so none stays a zombie until the sandbox ends. Not present: `/home`, `/mnt` (Windows drives), `/run` (sockets), WSL interop. Egress refuses loopback/private/link-local/CGNAT/ULA and dials the IP it vetted; with an `egress` list for the run's role it also refuses every host off the list and records each refusal and its reason in `turn-NNN.jsonl.egress`; a granted loopback ip:port is dialled as that literal address (macOS runs one proxy per command for the same).
