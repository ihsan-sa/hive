# Architecture

One Go binary, `hive`. A small core plus default modules; the daemon runs both and serves the control center over localhost.

## Packages

| Package | Role |
|---|---|
| `internal/core` | **The core.** Journal (append-only event log), workspace + config, runs (agent turns, park/resume, crash retry, reattach), mailbox ops, effects process (git/forge, commit extraction, gate guarantees), project registry, token source, person queue, ceiling notes. ~3k lines. |
| `internal/sandbox` | Linux namespaces (`sandbox-exec` outer + `sandbox-init` pid 1), WSL launcher (Windows), Seatbelt (macOS, untested), bare (opt-in). Egress proxy. |
| `internal/harness` | Adapter seam. Claude Code (`claude -p --output-format stream-json`), Codex (`codex exec --json`; inside our sandbox with its own off, since its bubblewrap can't nest; bare, in its own read-only or workspace-write sandbox; usage read from its session rollout at turn end), open (`hive open-agent`: any OpenAI-compatible endpoint; [models.md](models.md)), fake (scripted). |
| `internal/proc` | Detached processes; liveness by pid + start time, and a zombie is dead, though stopping one still signals its group. |
| `internal/agentcli` | `hive agent <op>`: what agents call from inside the sandbox. |
| `internal/fakeagent` | `hive fake-agent`: scripted agent for tests and dry runs (FAKE:* keywords). |
| `internal/openagent` | `hive open-agent`: the open harness's agent loop over an OpenAI-compatible chat endpoint (Ollama, OpenRouter), with shell and file tools, writing Claude's stream-json. |
| `internal/mod/*` | Default modules: `agents` (prompts, spawner), `chat`, `work` (ask → merge), `improve` (measure, keep/revert, sweep), `kb` (notes, the record filed from the journal, search), `system` (schedules, wake-ups), `risk` (requests past the sandbox → warden, tribunal or person), `projects`, `modules` (registry, installs, updates, the tick list), `runner` (modules that carry a program), `release` (self-update, self-release), `tools` (runtimes agents install for themselves), `feedback` (what agents tell the person about the Hive; [feedback.md](feedback.md)), `models` (the lead's route and trial ops, trials' records; [models.md](models.md)), `report` (opt-in failure reports to the developer, scrubbed; [report.md](report.md)), `scan` (the identity and secret scan on every release and on `hive share`), `stats` (the dashboard's spend, recent activity and all-time totals, a running tally of the journal). |
| `internal/app` | Wires core + modules; the tick loop steps the core, then each module the registry lists. |
| `internal/daemon` | `hive daemon`, control API (127.0.0.1, bearer token in `.hive/private/daemon.json`, 0600). |
| `internal/api` | API types + client. |
| `internal/tui` | Control center (Bubble Tea): Chats, Dashboard, Waiting, Feedback, Knowledge, Modules, Settings. |
| `internal/text` | `Visible`: spells out control, bidi and zero-width characters so text from outside (the usage feed, ask titles) can't rewrite the terminal. |
| `internal/setup` | First run, `hive login`, `hive doctor`, autostart (HKCU Run / systemd user / LaunchAgent). |
| `modules/` | Default module content (orientation + role prompts, manifests), embedded and written to `.modules/` on first run. |
| `internal/demo` | Demo project template (textkit: tests + score). |

## Folder on disk (`~/hive`)

```
.hive/      events.jsonl, config.json, chats/*.jsonl, scores/*.jsonl,
            runs/<id>/{host,ro,box}, kb/ (git repo of notes; record/ filed from the journal, untracked), gates/, checks/, improve/sweeps/,
            logins/, private/{daemon.json, update.json, runs/<id>/{home,codex,codex-sessions}},
            tools/<python|uv|node|go>/bin (agent-installed runtimes; read-only at /hive/tools, on PATH),
            reports/{sent/*.json, outbox.jsonl, pending.jsonl} (only when sharing is on)
.modules/   agents, chat, kb, improve, system, + installed (each with .hive-source.json)
projects/<name>/             host clone (effects process only)
projects/<name>/.checkouts/  agents' own checkouts (excluded from the clone)
```

Run dir: `host/` (turn output, prompts, stop file; never mounted on its own), `ro/` (system prompt, brief, inputs; mounted read-only at `/hive/run`), `box/` (mailbox + notes; rw at `/hive/box`); its home (rw `$HOME`) is `.hive/private/runs/<id>/home`. Every run but an isolated project's also gets the whole `.hive` read-only at `/hive/state` (`$HIVE_STATE`), so agents read one another's runs, chats and records. What grants access lives in three folders covered there as a whole (an empty tmpfs; a Seatbelt deny on macOS, after which a run's own writable folders are allowed again): `logins/`, `modules/` (module programs' homes and logs) and `private/`, which holds the daemon's token and every run's home and `CODEX_HOME`. Covering folders rather than files means a run made mid-turn, or a `daemon.json` a restart renames into place, is covered too; a file cover is bound to the inode it found. On its first start on this layout the daemon ends the turns the earlier daemon left running (their mounts carry no cover over `private/`), then moves homes and Codex homes from where earlier versions kept them and deletes their turn specs (docs/risk.md, Updates). config.json and daemon.log hold nothing that grants access. A turn's spec, which carries its token, is written to the temp dir. A project shares at one of three levels (docs/sharing.md): shared, private (covered from the rest as an isolated one is, while its runs mount the shared Hive like a shared project's) or isolated; below, "isolated" covers private too except where a run's own view is meant. Also covered is everything an isolated project leaves in the shared Hive: its clone under `/hive/projects`, its runs' folders and chats, its `checks/`, `gates/`, `risk/` and `kb/isolated/` folders, its runs' scratch folders, its scores, and while any project is isolated the whole journal, since one file holds every project's events (`Runs.hideIsolated`); an isolated run sees no other isolated project's notes. No agent outside an isolated project can spawn into it, file work in it, message or list its agents or see it in `status`, and its agents reach no other project (`Runs.Walled`, judged from the core's record of each run) nor create one, whose name, description and goals would land in the shared record. Records from before these folders (old notes, `risk/<id>`, `checks/<id>.log`) move into them on start, and whenever main's history in the knowledge base still holds a note naming an isolated project (checked every start, so a project isolated later or a rebuild cut short is caught next time), that history starts afresh and the filer's old clones go, so the old text can't be read back from git (a clone of the knowledge base made before shares no history with it after). A run or chat that starts mid-turn shows until that agent's next turn, and a bare run (no sandbox) can't cover anything.

Tools: `hive agent install --tool python` runs `hive tools-fetch` in a sandbox of its own that may write `.hive/tools` (network through the egress proxy, held to the asking run's egress list; on Windows inside WSL, so the builds are Linux ones). uv, node and go come from their official downloads, checked against the official sha256 before anything is replaced; python is `uv python install`, which checks its own. The person is told after each install. `--system "<command>"` (root) becomes a person ask with that exact command. On host paths (bare, Seatbelt) the tools folder's bins come first on PATH, so an installed runtime wins over an older one beside hive.

## Data flow: one ask

1. Person → chat → lead run (persistent Claude session, resumed per message; Claude Code compacts it when full, and the lead keeps its journal in its box `notes.md`, which a replacing lead inherits).
2. Lead → `hive agent brief` → `task.saved` (stage `new`).
3. work.Tick: issue (idempotent by body marker) → worker run `w-<task>` in a fresh checkout at main → worker `finish`.
4. Effects.Extract: `git bundle` made **inside the sandbox**, fetched into the host clone with fsck, must descend from the recorded base → push `hive/<task>` → PR (idempotent by head branch).
5. Effects.RunCheck: tests on the exact sha in a fresh clean clone, sandboxed; command read from **main's** `.hive/project.json`.
6. Small (docs-only, ≤40 lines, no protected or high paths, not a self project) → merge. Else reviewer run (read-only tools, JSON-schema verdict) bound to the sha; a change to a `high` or `root` path in `.hive/project.json` (a self project also always has `core.SelfRoot`/`core.SelfHigh`, see root-paths.md) needs a second land from a separate reviewer run on the same sha.
7. Fix verdict / red tests → same worker, same checkout, bounded rounds (default 3) → stop with PR open. A host-made revert has no worker: its reviewer gets a revert brief, and findings stop it with the PR open.
8. Merge: main moved → the PR merges as it is while the forge says it merges cleanly (`Mergeable` MERGEABLE), since each main merge moves the head past its reads and restarts its checks; only a conflict, or the forge's rule that the branch be up to date (`MergeState` BEHIND), has the host merge main into the branch (host-made commit; the read carries while the change's own diff is the same) → retest; while the forge is still working it out (UNKNOWN), it waits under a saved `waiting …` reason, so one that never resolves reaches the lead through improve's stall watcher. A hold says so on the PR once per `work.HoldKey` (its reason with the parentheticals, such as the pending check names, left out). A PR whose changed paths match main's `tests/LANDING-security.toml` `paths` (`Change.Security`; `*` within a segment, `**` across; decided by paths alone, never by what the worker wrote) waits first, with one line on the PR, for its security read on its own diff (`Effects.SecurityOK`). The Hive gives it: a security seat (`s-<task>-<diff>-security-<n>`, named by the own diff so a caught-up head finds it reading), a read-only reviewer run on the first `tribunal_models` seat whose model isn't the reviewer's, briefed on the sandbox, credentials and what runs outside it; then, for a file on the list's `root` entries or the project's root class (`Change.SecurityRoot`), a panel of `core.PanelSeats` such runs spread over the tribunal seats, one round, whose majority of lands passes and majority of fixes sends it back. The host sets each run's `seat` input, so a seat's verdict (`Verdict.Seat`) never counts as an ordinary read, nor the other way. An outside read the person records with `hive read <task|#pr> <sha> land|fix --by perms|architect` (`POST /api/read`, the person's token only) counts in their place; its fix, or the seat's, goes back to the worker. Then the forge's own checks on that exact head (GitHub check runs, the newest attempt of each, statuses, and a GitHub Actions suite under 10 minutes old with no jobs listed yet as pending): each name in the list's `required_checks` must have succeeded there (missing, neutral or skipped holds like one still running; with none required, no checks pass); one still running holds; a failure goes back to the worker as a red test does, except one main fails at its head too (`core.ChecksAgainstMain`, used by the gate and again by `Effects.Merge`): a change whose every failure main shares is no worse than main and merges once the rest pass, so the fix for a red main can land, its log naming the checks red on both, a PR comment saying so, and a `main-red` alert raised once. Inside a shared check the failing tests its log names (`Effects.FailingTests`, GitHub Actions job logs, `core.FailedTests`) are compared with main's: a test main's run doesn't fail makes the check the change's again; a log that names none leaves the check name to decide, and the PR comment says a new failure there can't be ruled out. If GitHub's branch rules still refuse the merge (a required check red on both), `Effects.Merge` returns `core.RefusedRed` and the task holds with that reason and one `main-red` alert instead of counting errors toward a stop; one that can't start (startup failure, cancelled, queued over an hour) is the environment's: the change waits and a `main-red` alert is raised once. The own diff is taken with `--binary --full-index`, so two different binary blobs never share a read. In a self project, last of all, for a task aimed at a gain (`Task.Aim` = `gain`; a fix skips it), the recursive gate (`work/selfgate.go`, docs/gate.md): the daemon runs `hive gate` on the exact head against main, one at a time, with no ties allowed, and `Effects.Merge` refuses such a self merge (`MergeRequest.Gain`) without a recorded keep (`gate.judged`) on that head and main. `gh pr merge --squash --match-head-commit <sha>`.
9. Checkpoints (scored projects): while a worker runs, a change to its checkout's reflog makes the host extract its newest commit and score it; one that beats the best kept score (or the last checkpoint's, until main is measured) by more than the tolerance goes through steps 4-8 as a checkpoint on `hive/<task>[-n]`, its PR not closing the issue. Red tests, a fix verdict, a conflict or a "leave open" drop it with the worker untouched. Once merged, the task's base moves to that commit and the worker is told at its next prompt; later commits are laid onto main with that commit as the merge base (`UpdateBranch`, `git merge-tree --merge-base`), since main holds it squashed. A finish with nothing past the last checkpoint is done. Each merged checkpoint keeps its PR on the task (`Banks`), so a revert of it names that PR. A commit is weighed once; a worker sent back after its finish, or whose checkpoint the person left open, gets no more checkpoints. A worker that rewinds past a merged checkpoint is told to bring it back. The merge base needs git 2.40 or later; on an older git it's an error, not a conflict.
10. improve: measure merge sha (tests + score) — unless a main commit already measured contains it (a PR that landed before its task closed): then only `score.covered` names that commit, with no score, alert or revert — compare with best kept; worse → revert task (host-made revert + lessons line) → PR → merge; original PR commented. Red tests are read from the full check log for the failing packages, tests and assertions (that line is the note and the lesson), and what failed runs once more (`retest`: only the failing tests and packages under the project's go test flags): a pass is a flake, so the merge is kept, a `flaky` alert raised and the test filed as work. Still red, but every failing test also failed within 72h at a commit without the change (checked before the merge, none of the task's heads or checkpoints), is a flake too → `flake` alert, no revert.
11. release (self projects, one at a time per project): on a kept merge, list the merges after the one the last release was cut at, up to this one, with the reviewer runs that read each exact head; a merge a newer release already covers is refused with an alert; a head with no read or a change to a `root` path waits for the person's "release" (approval kind `release`, kept apart from a `merge` approval of the same sha), and a newer hold supersedes the older ask; the identity and secret scan (`internal/mod/scan`: the commit's files that its `.hive/public.txt` names, against the deny and handle lists in `.hive/private/scan-deny.txt` and `scan-handles.txt`; no handle list, or any key, deny word or handle, blocks with an alert that names file, line and kind only); dry run; release with that list in its notes, as a pre-release, numbered on from the newest release (a pre-release included). The release module's tick (`Publish`, every 10 minutes) makes it the latest, which installs and auto-update follow, once `ci` and `update` pass in its own release runs on its commit; the newest of the waiting pre-releases that passed wins and older ones stay pre-releases; a failed run raises one alert and leaves it a pre-release (a re-run that passes publishes it); one waiting over 6h is raised once. Right after the cut and again before publishing, the tag's commit is read (`TagCommit`, `commits/refs/tags/<tag>` on GitHub); a tag at another commit (made outside the Hive) journals `release.refused` and alerts. The release stays a pre-release, its merges wait for the next one, and the alert tells the person to reject that tag's release-signing run, since the pre-release already started release.yml there, and then delete the release and its tag. A tag that can't be read at the cut is alerted and recorded as `tag_unread` in `hive.released`, and Publish waits until it reads.
12. Stalls (`improve/stalls.go`, every tick): a task stage, or a run no task owns (warden, tribunal seat, helper), that has gone longer without moving than `max(stall_floor_seconds, 3 × p90 of that stage's recent durations here)` gets its hung turn interrupted once (the core retries it on the same checkout), then is handed to the lead. Moving means the stage changed or the run started a turn or wrote output; parked, quiet and waiting runs and person-waiting tasks are left alone. Each decision is a `stall.saved` event with the limit and sample count, listed in the sweep's digest, and one `alert.raised` per thing, keyed so it updates in place.

## Modules that run a program

A module's `module.json` may name a program and the hooks it serves, so a door (a chat service, mail), voice or a resource lease can be added on top of the released binary instead of a fork of it:

```json
{"name": "door", "exec": ["./door", "--quiet"], "hooks": ["source", "channel"]}
```

The program can be in any language. The daemon starts it from the module's folder (a first word starting with `.` is relative to it) and keeps it running: one that exits is started again after a pause that doubles from a second up to five minutes, and resets once it has run a minute. Its output goes to `.hive/modules/<name>/module.log`. The daemon journals `module.started`, `module.exited` and whatever the module reports. Built-in modules stay in-process; the tick list is the registry's (`Registry.Builtin`), and the runner is one entry on it.

**The module calls the API; the daemon never calls the module.** Each start gets a fresh random token in `HIVE_MODULE_TOKEN`, with the API's address in `HIVE_API`. The daemon keeps the token in memory only, and it dies with the process. A request with a module's token reaches only the endpoints its hooks name, and anything else gets 403. Its token also reaches only the projects the person granted the module (`.hive-source.json` `projects`, set from the Modules screen): an ask, a chat, a run or a task in another project is refused, `/api/events` leaves out their events, and anything with no project, such as the lead's chat, the person's asks and the lead's runs, needs a grant of `*`. The only project-less events every module reads are the workspace notices: `hive.idle`, `hive.started`, `hive.stopped`, `alert.raised` and `module.*`. A module's chat posts are tagged with its name, and the lead reads them as `Module <name>: …`. The registry is the one list of which modules exist, what they serve and which projects they reach. Hooks are read off the journal (`/api/events?after=<seq>`), so a module that was down catches up from where it left off and the daemon never waits on a module. A module's read returns the first 2000 events after its cursor, so catching up never skips a gap. Calls the other way would mean the daemon blocking on a slow program, a second listener per module and a second protocol. A token must come as `Authorization: Bearer <token>`; any other form is refused.

| Hook | What it is for | API it may call |
|---|---|---|
| `source` | asks arrive from outside | `POST /api/ask`; the task's `from` is `<module>/<from it gave>`, so an ask carries where it came from |
| `channel` | the lead's conversation and run notices out; steer and stop lines in | `/api/chat` (read and post), `/api/events`, `/api/run/stop`, `/api/task/stop` |
| `after` | a step after a run or a merge ends | `/api/events` (`run.turn_ended`, `effect.merged`) |
| `status` | read the journal's events | `/api/events` |
| `idle` | act when nothing is running | `/api/events` (`hive.idle`, journaled when the last running or queued run ends) |
| (every module) | | `/api/ping`, `POST /api/module/report` (journaled as `module.reported`) |

**Trust.** A module's program is not sandboxed: a door needs the network and the API on localhost, and a lease needs devices. It runs as the person, so it can read anything the person can, including `.hive/daemon.json` (which holds the person's own API token) and the person's `gh` and `ssh` config on disk. The review gate below is therefore the trust boundary. The scoped token and the scrubbed environment only keep a well-behaved module to its hooks; they don't stop a hostile one. A module installed from git is cloned only on the person's "install", and its program starts only once a read-only review run (`module-reviewer`, scratch copy of its files, structured `approve`/`decline`) has read it at the commit checked out, and the brief names that commit. An update moves the commit, so it stops and is read again before it runs. A decline raises an alert and the program stays stopped. A review that ends with no vote (it failed or crashed) is not a decline: it runs again, up to three times in one life of the daemon, then raises one alert and waits until the person presses `r` on the module in the Modules screen (`/api/module/review`) or restarts the Hive. A clone whose install failed is removed, and a folder with `.git` but no source record is read like any other git module. A module the person put in `.modules/` by hand, with no `.git`, runs as it is. The program never holds the forge credential: its environment drops forge and model tokens and the person's config folders, `HOME` is its own `.hive/modules/<name>/` (covered in every agent's `/hive/state`, so no run reads its login or log), and no scope pushes, merges or reads secrets, so effects stays the only holder.

**Against an in-process hook table.** The other way to build this is a hook table: the loop loads each listed module's file by path and calls its hooks in its own process, a door's hooks come from the registry, and a run gets only the modules its row grants. Each credentialed relay stays in the effects process as a verb with a checked shape. The Hive keeps two parts of that: the registry is the only list (the tick list and the grants both come from it), and the credential never leaves effects. It parts ways on who calls whom. An in-process hook table means every module is trusted code in the daemon, written in its language. Here a module can be any program, so the daemon can't call into it safely or cheaply. Instead the module pulls a scoped slice of the API and reads the journal, and a slow or dead module never holds the daemon up. Built-in modules still run in-process, as a hook table would.

## Invariants (enforced by structure)

- A module program's environment carries no credential, and its token reaches only its hooks' endpoints; its review, not the token, keeps it from the person's files.
- Agents hold no credentials. Sandbox gets `CLAUDE_CODE_OAUTH_TOKEN` = short-lived access token only, read fresh per turn; each Codex turn gets a fresh `CODEX_HOME` made on the host side (`private/runs/<id>/codex`, mounted at `/hive/codex`), so nothing the agent planted steers the write; its `auth.json` holds the access token with the refresh token blanked and its `config.toml` the Hive's instructions (argv has a size cap). At turn end it is deleted except `sessions/`, kept in `private/runs/<id>/codex-sessions` for resume; folders the agent locked are opened first, a removal that still fails blocks the run, and daemon start deletes any left by a crash before a turn began. A bare run whose machine login has no readable credential file gets no token, so the harness's own host login works. Each turn goes on the least-used login of the pool (by the fullest of its usage windows still running, `Plan.Used`; the machine's own plus `.hive/logins/<harness>/<name>` from `hive login add`, which refuses a Codex API-key login since it has no access token to hand a turn) not parked at its usage limit. The host's own logins are renewed by the daemon (`Tokens.Watch`, every minute) in their last minutes (Claude Code renews only within five of the expiry, Codex only once the token is turned away): the harness is found by absolute path (PATH, then `~/.local/bin` and the other usual folders, since a service's PATH lacks them), and a renewal counts only if it exits 0 and the expiry moves. Its harness is also tried hourly with `--version`, so one that can't run is told hours ahead. Every failure is a `login.renew_failed` event and a daemon.log line, backs off 1 to 15 minutes, and the first of a run raises one alert (ref `login:<key>`) and a `login` ask with what to run; a later success, or an expiry that moves past the one it failed at (renewed by hand), replaces the alert and closes the ask. A restart reads an unresolved failure and its count back from the journal, so it isn't told afresh. Only harnesses some route uses are watched (`Config.Uses`); a harness binary inside `.hive/` or `projects/`, which runs can write, is refused, and the harness's output is scrubbed of token-shaped strings before it reaches the journal. The control center lists each login's expiry and last renewal.
- Host git never runs in an agent's checkout (only in host clones and fresh gate clones; hooks disabled, fsck on fetch).
- Only `hive/*` branches are pushed; main changes only by merge; `PushInitial` only into an empty repo with a host-made commit.
- Merge requires: host-recorded passing test on that sha + (small | land verdict from a core-started read-only reviewer on that sha's own diff | host-made revert/setup) + an approval if protected paths changed (the person's at autonomy 1, else a warden's; `risk.Weigh`) + each of main's `required_checks` succeeded and no forge check failing, can't-start or running on that sha + for a path on `tests/LANDING-security.toml`, a security read that said land on its own diff (the Hive's security seat, with its panel's majority for a root path, or an outside read from perms or the architect, whose fix outweighs any land). A read is bound to the diff its reviewer was given (`core.DiffID`: the change's own diff from its merge base with main, `--binary --full-index`, hunk positions and text files' blob-id lines left out; a binary file keeps its index line, since its delta is relative to the old blob), so it carries to a head with main merged in only while that own diff is unchanged; a merge whose conflict resolution touches the change's own files needs a new read. Any `.gitattributes` is high class, since it picks merge drivers. A high class needs two land runs since the last fix.
- Files the sandbox can write are read with `SafeRead` (no symlinks, same-file check); the host decides what to kill/clean from its own records.
- Nothing an agent requests runs outside the sandbox, except a script a warden or tribunal approved, run by the risk module in the daemon as exactly that digest-pinned script text (the pin covers the text, not files it calls); what is always the person's goes to the person (see [risk.md](risk.md)).
- Every state change is a journal event; restart = replay + reconcile; issue/PR/run creation is idempotent.
- One daemon per workspace: `hive daemon` takes an exclusive lock on `.hive/private/daemon.lock` (flock; LockFileEx on Windows) before it touches anything, and a second one exits at once naming the pid, start and starter written there (`daemon.AlreadyRunning`), whatever started it. A holder that doesn't answer is on its way out (ping fails once shutdown begins) or still starting, so a plain start waits up to 30s for its lock and exits at once only when a daemon there answers. An update's restart (`--wait-for`) waits up to 20s for the daemon it replaces to let go; a hand-off to systemd or to a renamed binary lets go first.
- One launcher: a command that finds no daemon waits for one that holds the lock but hasn't written `daemon.json` yet, and when the Hive's systemd user unit serves the workspace it has systemd start the unit instead of a detached daemon beside it; enabling the unit removes a desktop autostart left from a start without systemd.
- One process per turn: before a turn starts, the daemon claims it in `runs/<id>/host/turn.claim` (its pid and start, the turn, then the turn's process) under a lock on `turn.lock`; a claim for that turn or a later one by another live daemon makes it back off, and a dead daemon's claim is taken over only once the turn it started has ended (`core/claim.go`).

## Left alone on a shared machine

Settings in `.hive/config.json`; none of them stops or parks work.

- `max_output_tokens` (16000): sets `CLAUDE_CODE_MAX_OUTPUT_TOKENS` on each Claude turn, because a spend budget is checked only between turns and one reply can otherwise run long. 0 leaves Claude's own default.
- `monthly_usd` (off): each turn's `cost_usd` is already in its `run.turn_ended` event; the runs fold it into a total per UTC month. Past the figure, the person is told once that month in the feed (`Person.Tell`, id `spend-YYYY-MM`).
- `mem_floor_mb` (1024), `mem_pressure_max` (10), `cpu_pressure_max` (40): before a turn starts, Linux's `MemAvailable` and memory and CPU pressure (`/proc/pressure/memory` and `cpu`, some avg10) are read. Past any limit the run waits, keeping its status, backoff and nudges, with the reason shown in the control center (`run.held`), and starts on the first tick after the machine recovers. Where those files don't exist (macOS, Windows) nothing is held; 0 turns a check off.
- `max_workers` (4), `load_max` (1): a filed brief becomes an issue and then waits as `queued` (`internal/mod/work/queue.go`). Each tick starts the queued briefs in order (the lead's `queue --order` first, then as filed), only while fewer than `max_workers` tasks are working (the plan's limit until its usage reading is trusted), the machine isn't strained (the three limits above) and its 1-minute load per core is at most `load_max`. A brief naming a file (a path that exists in the project) that a brief being worked on or ahead of it in line names too, or a directory that holds the other's file, waits until that worker is done: a file is only itself (two files of one package start together), a directory counts only when a brief names it, never at the top level, a `merge=union` file (`.gitattributes`) is no area, and a task past working (landing, testing, reviewing, merging) holds nothing back, since a later conflict goes back to its worker with main; `queue --hold` keeps one back; `queue --now <id> --why` starts one past that overlap (journaled with the reason, still within the caps). `landed --task <id> --why [--merge sha]` (lead) ends a task in any stage as merged when its PR is MERGED on the forge or main holds its head (squashed: the named main commit must hold it, `merge-tree` adding nothing), recording the merge and running `OnMerged`, so what waits behind it starts (`internal/mod/work/landed.go`). Each waiting brief shows why. Nothing here stops a started worker, and a lower cap only holds new starts. 0 turns a limit off.
- `max_checks` (cores/6, at least 2; 3 on 20 cores): the gate's test, score and dry-run checks and improve's measures (`Effects.RunCheck`) take a slot first (`core.Slots`); the rest wait in the order they asked, shown under **checks** in the control center and in `hive agent status`. The stall watcher times a check from when it got its slot. 0 is no limit.
- `check_cache_max_mb` (8192): checks have room (`core/disk.go`). A check's home is `.hive/cache/homes/home-*`, its own and removed after; past this cap its stop file ends it as can't-run. A Go project's check (on a Linux sandbox with its own paths) gets `.hive/cache/gomod` read-only at `/hive/gomod` with `GOMODCACHE`, `GOPROXY=off` and `GOFLAGS=-mod=readonly`, filled by the effects process with `go mod download` (`GOTOOLCHAIN=local`, `GOVCS=*:off`, `GOWORK=off`, no code of the commit's run) once per go.mod+go.sum (`.hive/cache/gomod-sums/<hash>`); a prefetch that fails leaves the check to fetch its own, as before. The build cache is never shared: one commit's check could plant outputs another's trusts. A check whose output says the disk or a quota is full (`disk quota exceeded`, `no space left on device`, ENOSPC, EDQUOT) is can't-run, with one `disk` alert naming what uses the room until a check runs again, and it starts the `hive.clean` job (hourly and at start): agents' checkouts whose run ended and whose task is merged or done (stopped or blocked ones after 7 days; reviewers', and runs with no task, after 24 hours; leads' after 7 days), check homes, clean checkouts and prefetch folders over 3 hours old, the module cache past 20 GB while no check runs; then it measures the Hive's disk use and the room on the workspace's and temp filesystems for the dashboard (`State.Disk`). A task's checkouts also go the moment it is merged or done.

## Sandbox (Linux / WSL)

Outer (`sandbox-exec`, host side): egress proxy on a unix socket in `/dev/shm`, stop-file watcher, starts init with `CLONE_NEWUSER|NEWNS|NEWPID|NEWNET|NEWIPC|NEWUTS` (uid 0 → person's uid). Init (pid 1): tmpfs root; binds `/usr /bin /lib* /etc /opt /var /srv` read-only (nosuid, nodev, locked flags kept); fresh `/proc`, `/tmp`, minimal `/dev`; the install of each host `python3`/`python`/`node`/`uv`/`go` that lives elsewhere, read-only at its own path (its install dir if it has a `lib/` beside `bin`, else the bin alone; never the home, a dot-dir right under it such as `~/.local` or `~/.cargo`, a dir holding the workspace, one of its covered folders (`Spec.Guard`, `Workspace.Guarded`) or a mount's host path (a python at /data/bin with the workspace under /data is bound as its bin alone), or anything when HOME is unset or can't be resolved), with its dir on PATH after the `/hive/` dirs; run mounts; tools at `/hive/bin` (one already on the inside PATH under a system dir, like a Node launcher, runs in place); `pivot_root`; root remounted ro; `lo` up; forwarder 127.0.0.1:3128 → egress socket, and one per granted local address (`egress.local`) that relays a CONNECT to it over the same socket. Command runs in a nested user namespace (no caps); init reaps every orphan reparented to it while it waits for the command, so none stays a zombie until the sandbox ends. Not present: `/home`, `/mnt` (Windows drives), `/run` (sockets), WSL interop. Egress refuses loopback/private/link-local/CGNAT/ULA and dials the IP it vetted; with an `egress` list for the run's role it also refuses every host off the list and records each refusal and its reason in `turn-NNN.jsonl.egress`; a granted loopback ip:port is dialled as that literal address (macOS runs one proxy per command for the same).
