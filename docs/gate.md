# The recursive gate

A candidate Hive replaces the current one only if it does better, measured the way the current one is: in a child Hive, on real work, on the same day. `hive gate` runs that. Code: `internal/gate` (decision, child sandbox, probes, install) and `cmd/hive/gate.go`; the benchmark is `TestBenchmark` in `internal/e2e`.

## What it does

For a candidate commit `--head` of the Hive's source `--repo`, and the current Hive's commit `--base`:

1. **Build.** For each side, a fresh clone, `git checkout --detach <sha>`, verified to be exactly that sha and clean. First `go build`, stamped with the version `0.0.0-gate.<sha>`, into a folder the side can write only during the build; the candidate's binary is copied out and hashed **before any of its code has run**. Then `go vet` and `go test -short` on the read-only checkout, with the binary read-only too. Before the build the gate runs `go mod download` in the side's checkout, outside the sandbox, so the modules its `go.mod` and `go.sum` name are in the module cache. This runs none of the side's code. With `GOTOOLCHAIN=local` it can't fetch a different Go, and with `GOVCS=*:off` it never runs git or hg against a URL the candidate chose: modules come only from the module proxy. The side then builds and tests offline (`GOPROXY=off`), against the cache it sees read-only. So a candidate that adds or bumps a dependency still builds. A side that does not build or fails its checks ends the gate: rollback.
2. **Child.** Each side is installed as a child Hive in a fresh sandbox: its own `HOME`, its own `HIVE_HOME` workspace and local forge under the run's `--out`, and an environment made from a whitelist (`PATH`, proxy, Go cache paths). The only credential it may hold is a **contents-only** token for the test repositories (`HIVE_GATE_CHILD_TOKEN` / `--child-token-file`); the token that makes and deletes repositories (`HIVE_GATE_ORG_TOKEN` / `--org-token-file`) stays with the gate, and the two must differ. Without a child token the org probe is skipped. Neither is the login of the repository being gated. Before it makes anything, the gate checks what the children's token reaches (`CheckReach`): it must be fine-grained, the test org must not own the repository being gated, and everything the token can push to or administer must be one of the gate's own `gate-<run>-candidate|control` repositories in the test org. An org-wide token on `Hive-RSI-Lab` while `Hive-RSI-Lab/hive` is there is refused. Since each run makes fresh repositories, the token has to cover the whole test org, so the passing setup is **a test-only org that holds nothing but the gate's repositories**: that org is the person's to make. The candidate's build, vet and short tests run in the child too, never on the host. The bubblewrap sandbox is an **allowlist**: the system dirs (`/usr`, `/bin`, `/lib*`, `/etc`, `/nix`, and `/run/systemd/resolve` for DNS) read-only, then only what the child is given: the Go toolchain (`GOROOT`, on its `PATH`) and module cache, read-only, since both often live under the person's home; its checkout and binary, read-only; its own root (home, workspace, `TMPDIR`, its own empty Go build cache), writable; the build output, writable only during the build. Nothing else of the machine is there: not the person's home, not a token file kept elsewhere, not another workspace and so not its daemon's token, not `/run/user` or the D-Bus socket (so `systemd-run --user` is out of reach). Own pid, ipc, uts **and network** namespaces: a sandbox has no network of its own, and its only way out is the side's **meter** (`internal/gate/meter.go`). The meter is an HTTP CONNECT proxy that the gate runs outside every sandbox, one per side. It counts the bytes each way, refuses this machine and private networks (so no daemon port or local service here is reachable), and chains to the gate's own proxy when it has one. Inside, `hive gate-fwd` (the gate's own binary, bound read-only) relays `127.0.0.1:3128` to the meter's socket and runs the command, and the side's `HTTPS_PROXY` points there. A deadline on any wait on a child kills its whole process group. Under bubblewrap that is the pid namespace, so nothing the child started outlives it. A child's output is kept to its last 4 MB. **Without bubblewrap the gate refuses to run**; `--allow-bare` runs the children bare (the same scrubbed environment and fresh home, no filesystem isolation), never with `--org`, and a bare run is never installed. The report says which (`sandbox`). `hive gate --self-test`, which only runs inside a child, allows bare by itself: it is in the child's sandbox already, on local repositories, with no token.
3. **Org repo.** With `--org Hive-RSI-Lab`, each side gets a fresh private repository (`gate-<run>-candidate|control`), made after the builds pass and deleted when the run ends however it ends. A run makes at most `MaxRepos` (4) of them; the report lists what was made, removed and, loudly, left. Deleting needs the token to carry `delete_repo`. `--local-org <dir>` uses bare repositories in a folder instead, for dry runs and tests.
4. **Real work, judged by one evaluator.** The `e2e` and `benchmark` probes run the tests of a third checkout, the **evaluator** (`--eval <sha>`, default the base), against each side's own binary, so a candidate cannot delete a failing test, change the asks or the timer, and win. The candidate's own tree is built and unit-tested but never grades itself. A change to the e2e suite or the benchmark therefore takes effect for the gate only once it is the base. The evaluator's tests are compiled by the gate (`go test -c`) with caches of their own, before either side's code runs.

   **No sandbox is started from inside another.** On Ubuntu with `kernel.apparmor_restrict_unprivileged_userns=1`, AppArmor's profile lets `/usr/bin/bwrap` make namespaces one level deep, but a bwrap started inside a bwrap is refused. The gate itself, the unsandboxed parent that runs no candidate code, therefore starts every sandbox, side by side. Each sandbox is marked (`HIVE_GATE_SANDBOXED=1`), and inside one, `BwrapWorks` is false without trying and `pickSandbox` refuses bubblewrap. `TestNoSandboxInsideASandbox` drives a whole run with a recording bwrap and fails if any bwrap is started from inside a sandbox. The compiled suite runs **inside the side's own sandbox**, because it must reach the side's daemon on the side's network, and a sibling sandbox has a network of its own. What keeps the side from bending the verdict there:
   - the suite and the evaluator's checkout are read-only to the side;
   - every process of the side's descends from the suite, and Yama (`ptrace_scope` 1 or more, which the gate requires) keeps a process from tracing or reading the memory of an ancestor;
   - the suite's exit code reaches the gate through processes the side cannot touch;
   - the benchmark's BENCH line carries an HMAC with a key the suite reads from its stdin before any of the side's processes exist, so a line the side writes into the suite's output is refused.

   The evaluator reads the side's forge with git, in that same sandbox (a repository's config is the side's writing, and stays there). The landed textkit source is passed on stdin to a **sealed** sandbox (`HIVE_E2E_CHECK`): the machine's programs, an empty root, no network, nothing of either Hive. The side's sandbox asks the gate for it over a socket (`hive gate-check`, served by a `Launcher`), and the gate starts it beside the side's. So nothing the side writes or serves decides an answer, other than the code that landed on its main. The suite must know the measure from outside (`HIVE_E2E_WRAPPED`); an evaluator older than that is refused, so until this change is the base, pass `--eval` at or after it. Probes, interleaved candidate/control for `--reps` repeats (default 3), so the day's weather hits both:

   | probe | what it does |
   |---|---|
   | `daemon` | the child's daemon starts on its fresh workspace, answers `status`, shuts down |
   | `org` | the child clones its org repo with the org token, pushes a commit |
   | `e2e` | the evaluator's whole `internal/e2e` suite against the child's own binary |
   | `benchmark` | `TestBenchmark`: a fixed set of asks on the demo `textkit` project (`HIVE_BENCH=<asks>`). The side is not taken at its word: what it says (a task is done, its score) only decides when to stop waiting. Judged: **score** (how many of textkit's six written-or-asked functions give the right answers on inputs drawn fresh for the run, with answers worked out by the evaluator), **asks_finished** (the asked functions among them), **seconds** on the evaluator's clock, and **egress_bytes**, the side's cost as its meter counted it, lower being better. Seconds and egress bytes are judged only between sides with the same score and asks finished (`Metric.Given`), so landing less, faster or cheaper never wins. **commits_landed** is the pass bar (one per ask) and is shown, not judged, so many tiny commits win nothing. `asks_done_reported` and `cost_usd_reported` are the side's own count: shown, not judged (`Metric.Info`). The fake worker writes the asked function, so the fake harness measures the pipeline's time and correctness. `HIVE_E2E_HARNESS=claude` makes it real work on real agents (plan usage) |
   | `recurse` | the child runs `hive gate --self-test`: the gate inside a child, gating a trivial change through a grandchild (its binary as both sides, so the right verdict is "not better"), on its own local org repos, which it must clean up. Inside the child's sandbox no sandbox is started, so the grandchildren run bare there, contained by the child's sandbox |

   More probes are added by name in `Config.Probe`; the live probes (`TestLive*`) are the e2e probes on a real harness.
5. **Decide.** `Decide` compares probe by probe and metric by metric. A probe the candidate passes less often than the control, or a metric worse beyond the noise, is a **regression**; the mirror is a **gain**. Noise is the larger of 2% of the control's mean and twice the standard error of the difference of the two means, so more repeats tighten it. **Keep only if there is at least one gain and no regression.** A tie is a rollback; `--allow-tie` keeps a change that is meant to move nothing (a docs edit) when it breaks nothing, and the caller says so. Without it a docs edit is rolled back as "not better".
6. **Record.** `report.json` and `report.md` in the run's folder, a line in `gates.jsonl` beside it. Three outcomes, each with its own exit code:
   - **Kept** (exit 0).
   - **Rolled back** (exit 1). The candidate is worse, or it failed on its own before it could be measured: it does not build, fails its own vet or short tests, or rewrote its binary. The reason is appended to `--lessons` (`.hive/lessons.md`), where the next worker reads it. The reason is Decide's words or a fixed phrase, never the candidate's output.
   - **Could not run** (exit 3, `cant_run` in the report). The gate itself could not run or measure: no bubblewrap without `--allow-bare`, no Go, Yama off, an evaluator older than the outside measure, the meter or the org failing, out of time, the clone or the module download failing, the control not building or failing its checks, a step (the build, vet or the short tests) failing on both sides, or a probe that failed on both sides (that path was never measured). This is not the candidate's failure, so **no lesson is written**: a check that can't find its own tool is "can't run", never red (see `.hive/lessons.md` on #111).

## Recursion and its caps

`--depth N` (default 1, at most `MaxDepth` = 2) is how many levels of gating the children may do; the child learns it as `HIVE_GATE_DEPTH` and `--self-test` refuses to run at 0. Each level makes at most 2 org repositories (the self-test uses local ones), and `--timeout` (default 2h) stops a run between probes.

## Installing a kept change, and going back

`hive gate ... --install <path>` installs only if the verdict is keep, the children ran under bubblewrap (a bare run is never installed), and the verified copy of the candidate's binary still has the sha256 taken right after the build, before any of its code ran, and the new install's `--version` names the version the gate stamped (`0.0.0-gate.<sha>`); a prebuilt binary has no stamped version and is never installed; a candidate that rewrote its own binary during the run is rolled back. Every report is signed: an HMAC over all of it, with a key the gate keeps in the person's config folder (`~/.config/hive/gate.key`, 0600), which no child sees. `hive gate install --report <run>/report.json --target <path>` installs a kept run later, through the same checks, and only from a report this machine's gate signed and nobody changed. A hand-written or edited report.json installs nothing. Anyone who can read the person's key could also just copy a binary into place, so the key guards against the children and agents, not against the person. Either way the install copies the current binary to `<path>.prev`, puts the new one in place, runs the health check (`--version` answers, and its last word is exactly the wanted version). The health check runs the new binary on the host, unsandboxed: it is the binary being installed, and **restores the previous binary if the check fails**. It does not touch the daemon's own updater (`internal/mod/release`), which keeps installing releases the way it did; wiring a gate in front of a release, and a health check after the updater's restart, is the next step.

## Where the sandbox is tested

ci's `sandboxed-e2e` job lifts Ubuntu's AppArmor user-namespace restriction and runs the gate's bubblewrap tests with `HIVE_GATE_BWRAP=1`, which turns their skip into a failure. The tests: the allowlist hides the host (`TestBwrapHidesTheHost`), the meter is the only way out and counts (`TestBwrapMeterIsTheOnlyWayOut`), sealed code runs in a sibling sandbox the gate starts on request, with no network and nothing of the side (`TestBwrapSealedCheckIsASibling`), the build and tests under bwrap (`TestBuild*`), a deadline kills a child's tree (`TestDeadlineKillsTheTree`), no sandbox starts inside another (`TestNoSandboxInsideASandbox`, which runs everywhere on Linux with a recording bwrap), and **a whole gate run** (`TestBwrapGateKeepsAndRollsBack`). That last one runs `Run` under real bubblewrap on a local org with the real probes: the daemon, the org round trip, the benchmark (inside each side's sandbox, its sealed check beside it, the meter as the only way out) and recurse. The keep run is a gate from commits: a trivial commit on a clone of this tree against the clone's head. The gate builds both (exact sha, stamped `0.0.0-gate.<sha>`, vet and short tests in the sandbox), judges them with the base's suite, which it compiles itself, and keeps the change with `--allow-tie`. The rollback run hands it a broken prebuilt candidate, which is rolled back with its lesson written. Both leave the org empty. A probe that fails on both sides is not an even result: that path was never measured, so the run could not decide (could not run). Its log in ci is the end-to-end record. Elsewhere they skip.

## On every change to the Hive itself

A self project's pull request (the Hive's own repository) merges only on the gate's keep (`internal/mod/work/selfgate.go`, issue #361). Once its tests, reads and the forge's checks pass, the daemon runs `hive gate` on the PR's exact head against main as the merge sees it, from its own binary on this host, so the children's bubblewrap sandboxes start one level deep, beside each other (never inside an agent's sandbox, which this host's AppArmor refuses). It never passes `--allow-bare`.

- **Keep**: it merges. `core.Effects.Merge` refuses a self project's merge without a recorded keep (`gate.judged` in the journal) for that head and main, or one carried to it (`Effects.GateKept`): as reads do, a keep holds for every head and main with the same own diff (`DiffID`, from the merge base), so a main that moves under an open PR without changing what the PR itself does doesn't send it round the two-hour gate again. A rollback on exactly that head and main, or a later rollback of the same diff, stops a keep carrying. The merge records how the gate let it through (`gate` on `effect.merged`: kept, kept on its diff against an older main, or waived by the person).
- **Only a signed report counts.** The daemon reads the verdict from `report.json` only if this machine's gate signed it and nobody changed it (`Report.Verify`, the check `hive gate install` makes); a report left behind or written by anything else is "can't run", never a keep or a rollback.
- **Rolled back**: the change goes back to its worker as a fix round, with the report in `$HIVE_RUN/gate-report.md` and the lesson line to add to `.hive/lessons.md`. The gate also writes the lesson to `.hive/gates/<project>/recursive/lessons.md` on this machine, and the next brief quotes it until main's lessons name the same commit.
- **Could not run** (no bubblewrap, no Go, out of time, no report): the PR waits as it is, never merged unjudged, with one alert; the gate tries again after an hour.
- A change that is only prose (`.md`, `.txt`, `.rst`, `.adoc`: docs and the agents' prompts) and a revert run with `--allow-tie`.
- One gate runs at a time; others wait their turn (`waiting for the recursive gate…`, which the stall watcher leaves alone). Each run gets `--timeout 2h`, and the daemon kills it 15 minutes past that; on Linux it dies with the daemon, and its sandboxes with it.
- Every verdict goes on the PR as a comment with the report, on the task (the control center's task view shows `gate` and `report`), and in the run's folder `.hive/gates/<project>/recursive/<run>/` (`report.md`, `report.json`, `gate.log`).
- The org: with both `/home/hive/h0-org.token` (the org's own, `core.OwnerTokens`) and `/home/hive/h0-gate.token` (the children's contents-only token), the gate runs with `--org Hive-RSI-Lab`, but only after `CheckReach` passes on the children's token. While `Hive-RSI-Lab/hive` (or any non-gate repository) is writable with that token, it refuses; the gate then runs on a local org and the PR and an alert say what the owner must move: transfer or delete those repositories, or mint the children's token without write on them.
- Under the fake harness (dev runs, the e2e) nothing real is built, so a stand-in keeps the change (`sandbox: fake`). Such a keep counts only while the harness is still fake: switch the harness to fake to collect a stand-in's keep and back, and `Effects.Merge` refuses it and the change is gated for real. A keep counts only from `bwrap` or, under the fake harness, `fake`.
- **A revert the Hive made itself** that the gate rolls back or can't run on has no worker to fix it, and undoing a bad merge mustn't hang on the gate. It stays held, with an alert, and the person is asked once per head and main (`gate` in Waiting) whether to merge it without the gate's keep. Only the person's answer waives it (never a warden's: the ask doesn't go through `Weigh`), only for a host-made revert (`Effects.GateWaived`).
- **The report may be public.** The verdict and `report.md` (up to 20 kB) go on the PR, which on a public repository anyone can read, and to the worker. Parts of it come from the children's output (a probe's detail, a build error's tail), which the candidate's code controls. So before the gate signs and writes the report it takes out the org and children's tokens (as themselves and as git's Basic value) and anything token-shaped (`ghp_…`, `github_pat_…`, `sk-…`, bearer and basic values, JWTs) from every text field (`Report.redact`). The lesson a rollback writes is Decide's words or a fixed phrase, never the candidate's output; the brief still treats lessons as data and quotes each as one plain line, clipped, with backticks and control characters taken out.
- The reach check on the children's token is cached for ten minutes, keyed by both tokens and the gated repository, so a token swapped for another is checked again at once; `hive gate` checks it again itself before it makes anything.
- The gate runs from an OS thread locked for its whole run: `Pdeathsig` fires when the thread that started a process exits, and Go retires idle threads, so started from any goroutine the gate could be killed midway.
- The number judged is the gate's own benchmark metrics until the score task (261024-073323-39b67b4b25) defines main's score.

## What is not yet done

- The release path does not run the gate itself; it cuts a self release only from merges the gate let through (`gate` on each `effect.merged` since the last release). A merge without one (from before the gate, or merged by hand) holds the release for the person, as an unread head does.
- No real gate has yet been driven by the daemon on the tower: only the stand-in and the shell fakes have exercised this path. The first self PR to reach the gate on a release that has it is that run; its verdict lands in the journal (`gate.judged`) and `.hive/gates/hive/recursive/`, and goes in `docs/gate-runs/`.
- A machine without a Go toolchain cannot gate.
- The benchmark is four asks. A real harness inside the allowlisted sandbox also needs the `claude` CLI and its login bound in, which the gate does not do yet. Cost is the bytes through the meter, not tokens: it tracks what a model costs (context sent, output received) but not price or cache discounts. A bare run has no meter it can enforce.
- Org runs need a test-only org and a fine-grained child token on it (both the person's to make) and the per-owner token (brief 261024-015755-a3f383a160); no org run has been made yet.
- The evaluator's scratch folder (`TMPDIR`, under the side's root) is writable by the side while a run goes on, because it holds the workspaces and forges the evaluator hands the side. The side can change what the evaluator keeps there. What is judged doesn't come from there: the forge is read through the side's own sandbox, the landed code runs sealed from source on stdin, and the answers and the clock are the evaluator's.
- The evaluator, the side and the grandchild are the same uid; the separation is namespaces, mounts and Yama, not users. The evaluator shares the side's sandbox: the side cannot reach into it (see above), but it can signal it, which only fails the side's own run.
