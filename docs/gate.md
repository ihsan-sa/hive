# The recursive gate

A candidate Hive replaces the current one only if it does better, measured the way the current one is: in a child Hive, on real work, on the same day. `hive gate` runs that. Code: `internal/gate` (decision, child sandbox, probes, install) and `cmd/hive/gate.go`; the benchmark is `TestBenchmark` in `internal/e2e`.

## What it does

For a candidate commit `--head` of the Hive's source `--repo`, and the current Hive's commit `--base`:

1. **Build.** For each side, a fresh clone, `git checkout --detach <sha>`, verified to be exactly that sha and clean. The candidate is judged **as it would land**: when its head lacks the base, the gate merges the base into it in its own clone (`git merge --no-ff`, no hooks, a fixed identity) and builds, tests and benchmarks that merge, so a bug main has since fixed (a test, say) is never counted against a branch cut before the fix. `report.json` records both: `head`, the candidate's commit, and `merged`, the tree it was built from (the head itself when it already holds the base). The version stamp stays the head's. A merge that conflicts ends the run as **could not run**, with the conflicting files in the verdict and in `report.json`'s `conflicts`; no lesson is written, since nothing was measured. First `go build`, stamped with the version `0.0.0-gate.<sha>`, into a folder the side can write only during the build; the candidate's binary is copied out and hashed **before any of its code has run**. Then `go vet` and `go test -short` on the read-only checkout, with the binary read-only too. Before the build the gate runs `go mod download` in the side's checkout, outside the sandbox, so the modules its `go.mod` and `go.sum` name are in the module cache. This runs none of the side's code. With `GOTOOLCHAIN=local` it can't fetch a different Go, and with `GOVCS=*:off` it never runs git or hg against a URL the candidate chose: modules come only from the module proxy. The side then builds and tests offline (`GOPROXY=off`), against the cache it sees read-only. So a candidate that adds or bumps a dependency still builds. A side that does not build ends the gate: rollback. The checks are judged **by test**: both sides run `go vet ./...` and `go test -short -json ./...`, and the gate names every failing package and test with the end of its output (in the verdict, `report.md`'s "Vet and short tests", `report.json`'s `unit`, and `gate.log`). A failure the control shares at the same base (same step, package and test) is the environment's: it is listed, never counted against the candidate, no lesson is written, and the run goes on to the probes. A failure on the candidate alone is run once more on the candidate (`-count=1 -run '^(TestX)$'`): if it passes then, it was a flake and is listed as one; if it fails again it is run on the control too, and only if the control passes it is it the candidate's own, a rollback whose reason names the package and test. Shared means the same failure: a package the candidate breaks whole (its tests don't build, a panic in `TestMain`) is shared only if the control fails that package whole too, never because the control fails one test in it. A failure in a package the control doesn't have (one the candidate adds) is the candidate's own, without asking the control. A rerun on the control that fails naming nothing, in a package it does have, shows nothing shared: could not run, with main to blame (`base_fails`). `go vet`'s bracketed header for a package's tests (`# [p]`) is read as package `p`. When vet checks a single package it prints no header, so its reports are put on the package of the file they name. A failure that names no test (output the gate can't read) on both sides is "could not run", with main to blame (`base_fails`).
   **Fixes** (`internal/gate/fixes.go`). Once both sides pass the step, the gate reads the candidate's own diff (from the base to the merged tree, so main's later changes are not the candidate's) and runs each test function it adds or changes (at most 20) on both sides. A change that touches no Go code outside its tests skips this. Both runs happen in one sandbox of their own (the candidate's kind, offline), at one path, with a fresh home and scratch each time: once on the candidate's tree, once on the control's tree with the candidate's `_test.go` files and `testdata` of that package in place of the control's. So the test is the same code on both sides, and only the code outside the tests differs. Each side runs each test alone (`go test -short -count=1 -run '^TestX$'`), twice, in an order the gate picks at random. A test counts as a **fix** only if, every time, it **passes on the candidate** and **fails by name on the control**, and on the candidate its coverage (`-coverpkg` of the changed packages) runs at least one line the diff added or changed outside the tests. A test that does not build or run on the control (it calls a function the change adds) is no evidence, not a gain. Since one such test keeps its whole package from building there, each test that passed on the candidate but did not build on the control is tried again, on both sides, with only its own file and the test files both sides have byte for byte (and the candidate's `testdata`), so a fix beside a test of a new function still shows; one that needs the candidate's other test files stays no evidence. Coverage is read only from the candidate's passing runs; one that fails on the control without running the change (it reads a file, say) is not counted either; one that passes on both is nothing. Each fix is a **gain** in Decide (step 5), so a bug fix or hardening the benchmark cannot see lands when its regression test shows it, and a change that moves nothing still ties. The report lists the tests tried, the fixes, why each other test did not count and how long the step took (`report.json`'s `fixes`, with `seconds`; `report.md`'s "The candidate's own tests on both sides"). The step is capped at 45 minutes. `TestBwrapFindFixes` runs it under bubblewrap, on a repo that needs a module from the cache, offline. The benchmark, the e2e suite and every other probe still come from the evaluator.

2. **Child.** Each side is installed as a child Hive in a fresh sandbox: its own `HOME`, its own `HIVE_HOME` workspace and local forge under the run's `--out`, and an environment made from a whitelist (`PATH`, proxy, Go cache paths). The only credential it may hold is a **contents-only** token for the test repositories (`HIVE_GATE_CHILD_TOKEN` / `--child-token-file`); the token that makes and deletes repositories (`HIVE_GATE_ORG_TOKEN` / `--org-token-file`) stays with the gate, and the two must differ. Without a child token the org probe is skipped. Neither is the login of the repository being gated. Before it makes anything, the gate checks what the children's token reaches (`CheckReach`): it must be fine-grained, the test org must not own the repository being gated, and everything the token can push to or administer must be one of the gate's own `gate-<run>-candidate|control` repositories in the test org, as GitHub answers the token itself. The `permissions` that `/user/repos` and `/orgs/<org>/repos` list are the owner's role, not the token's: a fine-grained token on one org still lists every public repository its owner has, marked admin. So the listing only rules out what the owner can't write; for each other repository (the gate's own aside) the gate probes with the children's token: a `POST /repos/<r>/git/blobs` with no content (GitHub answers 403 or 404 when the token lacks Contents write, 422 when it has it, so nothing is written) and `GET /repos/<r>/keys` (allowed only with Administration access). Repositories the token can only read, such as the owner's public ones, don't count. The probes run one at a time, paced under GitHub's secondary limit (600 points a minute of its 900; a POST costs 5 and a GET 1), so an owner with 300 public repositories takes about three minutes. The check stops at the first writable repository it finds. A secondary rate limit is waited out (its `Retry-After`, else a minute) and retried up to three times. Any other answer (a 5xx, a limit that doesn't lift) refuses the run rather than guess (`ErrReachUnknown`); the refusal names the repository and GitHub's answer (a 409 is an empty repository: push a commit to it or move it out of the org). A repository both listings return (an org's, under `organization_member`) is probed once. The daemon keeps an unknown for five minutes and a definite verdict for an hour, for one pair of tokens (a token changed on disk is checked afresh), and passes `--reach-checked` to the gate it starts after a pass, so a gate run doesn't spend another three minutes probing; a `hive gate --org` run by hand always checks. What the check proves: the token can't write contents or administer any repository but the gate's own. What it can't: the token's other repository permissions (issues, actions, secrets…) and its organization permissions (members, settings), which no API lists for a fine-grained token; and if GitHub ever validated a request body before the permission, a narrow token would be refused, never passed. Mint the token with repository permissions only: Contents read and write, Checks and Commit statuses read (Metadata read comes with it). An org-wide token on `Hive-RSI-Lab` while `Hive-RSI-Lab/hive` is there is refused. Since each run makes fresh repositories, the token has to cover the whole test org, so the passing setup is **a test-only org that holds nothing but the gate's repositories**: that org is the person's to make. The candidate's build, vet and short tests run in the child too, never on the host. The bubblewrap sandbox is an **allowlist**: the system dirs (`/usr`, `/bin`, `/lib*`, `/etc`, `/nix`, and `/run/systemd/resolve` for DNS) read-only, then only what the child is given: the Go toolchain (`GOROOT`, on its `PATH`) and module cache, read-only, since both often live under the person's home; its checkout and binary, read-only; its own root (home, workspace, `TMPDIR`, its own empty Go build cache), writable; the build output, writable only during the build. Nothing else of the machine is there: not the person's home, not a token file kept elsewhere, not another workspace and so not its daemon's token, not `/run/user` or the D-Bus socket (so `systemd-run --user` is out of reach). Own pid, ipc, uts **and network** namespaces: a sandbox has no network of its own, and its only way out is the side's **meter** (`internal/gate/meter.go`). The meter is an HTTP CONNECT proxy that the gate runs outside every sandbox, one per side. It counts the bytes each way, refuses this machine and private networks (so no daemon port or local service here is reachable), and chains to the gate's own proxy when it has one. Inside, `hive gate-fwd` (the gate's own binary, bound read-only) relays `127.0.0.1:3128` to the meter's socket and runs the command, and the side's `HTTPS_PROXY` points there. A deadline on any wait on a child kills its whole process group. Under bubblewrap that is the pid namespace, so nothing the child started outlives it. Bare, a daemon the child detached (setsid) has left that group, so every process a child starts also carries `HIVE_GATE_ROOT` (its root) and `HIVE_GATE_OWNER` (the gate's pid, start time and pid namespace): after each probe and as the run ends, however it ends, the gate kills every process whose environment names a root under its `--out`, or whose program or working directory lies in a folder the run made there (`gate.Reap`; a shell open in `--out` itself is left alone), and removes the run's checkouts, binaries and caches, and the project clones, binaries and tools in each child's workspace; every step of the removal stays inside `--out` (`os.Root`), so a symlink a bare candidate plants can't turn it on the host. Every log stays: each child's workspace (its `daemon.log`, journal, runs, `daemon-probe.log`), `gate.log` and the report. A bare child dies with the gate (`Pdeathsig`); a gate a person interrupts or terminates (SIGINT, SIGTERM) reaps its run before it exits; what it left when the gate was killed outright is ended by the daemon's `Reap` of the run folder once the gate exits (only a folder under `.hive/gates`), and by the next gate, which kills what carries the owner of a gate no longer running (`reapOrphans`). A child's output is kept to its last 4 MB. **Without bubblewrap the gate refuses to run**; `--allow-bare` runs the children bare (the same scrubbed environment and fresh home, no filesystem isolation), never with `--org`, and a bare run is never installed. The report says which (`sandbox`). `hive gate --self-test`, which only runs inside a child, allows bare by itself: it is in the child's sandbox already, on local repositories, with no token.
3. **Org repo.** With `--org Hive-RSI-Lab`, each side gets a fresh private repository (`gate-<run>-candidate|control`), made after the builds pass and deleted when the run ends however it ends. A run makes at most `MaxRepos` (4) of them; the report lists what was made, removed and, loudly, left. Deleting needs the token to carry `delete_repo`. `--local-org <dir>` uses bare repositories in a folder instead, for dry runs and tests.
4. **Real work, judged by one evaluator.** The `e2e` and `benchmark` probes run the tests of a third checkout, the **evaluator** (`--eval <sha>`, default the base), against each side's own binary, so a candidate cannot delete a failing test, change the asks or the timer, and win. The candidate's own tree is built and unit-tested but never grades itself. A change to the e2e suite or the benchmark therefore takes effect for the gate only once it is the base. The evaluator's tests are compiled by the gate (`go test -c`) with caches of their own, before either side's code runs.

   **No sandbox is started from inside another.** On Ubuntu with `kernel.apparmor_restrict_unprivileged_userns=1`, AppArmor's profile lets `/usr/bin/bwrap` make namespaces one level deep, but a bwrap started inside a bwrap is refused. The gate itself, the unsandboxed parent that runs no candidate code, therefore starts every sandbox, side by side. Each sandbox is marked (`HIVE_GATE_SANDBOXED=1`), and inside one, `BwrapWorks` is false without trying and `pickSandbox` refuses bubblewrap. `TestNoSandboxInsideASandbox` drives a whole run with a recording bwrap and fails if any bwrap is started from inside a sandbox. The compiled suite runs **inside the side's own sandbox**, because it must reach the side's daemon on the side's network, and a sibling sandbox has a network of its own. What keeps the side from bending the verdict there:
   - the suite and the evaluator's checkout are read-only to the side;
   - every process of the side's descends from the suite, and Yama (`ptrace_scope` 1 or more, which the gate requires) keeps a process from tracing or reading the memory of an ancestor;
   - the suite's exit code reaches the gate through processes the side cannot touch;
   - the benchmark's BENCH line carries an HMAC with a key the suite reads from its stdin before any of the side's processes exist, so a line the side writes into the suite's output is refused.

   The evaluator reads the side's forge with git, in that same sandbox (a repository's config is the side's writing, and stays there). The landed textkit source is passed on stdin to a **sealed** sandbox (`HIVE_E2E_CHECK`): the machine's programs, an empty root, no network, nothing of either Hive. The side's sandbox asks the gate for it over a socket (`hive gate-check`, served by a `Launcher`), and the gate starts it beside the side's. So nothing the side writes or serves decides an answer, other than the code that landed on its main. The suite must know the measure from outside (`HIVE_E2E_WRAPPED`); an evaluator older than that is refused, so until this change is the base, pass `--eval` at or after it. Probes, interleaved candidate/control for `--reps` repeats (default 3), so the day's weather hits both:

   | probe | what it does |
   |---|---|
   | `daemon` | the child's daemon starts on its fresh workspace, answers `status`, shuts down |
   | `org` | the child clones its org repo with the org token, pushes a commit |
   | `e2e` | the evaluator's whole `internal/e2e` suite against the child's own binary |
   | `benchmark` | `TestBenchmark`: a fixed set of asks on the demo `textkit` project (`HIVE_BENCH=<asks>`). The side is not taken at its word: what it says (a task is done, its score) only decides when to stop waiting. Judged: **score** (how many of textkit's six written-or-asked functions give the right answers on inputs drawn fresh for the run, with answers worked out by the evaluator), **asks_finished** (the asked functions among them), **seconds** on the evaluator's clock, and **egress_bytes**, the side's cost as its meter counted it, lower being better. Seconds and egress bytes are judged only between sides with the same score and asks finished (`Metric.Given`), so landing less, faster or cheaper never wins. **commits_landed** is the pass bar (one per ask) and is shown, not judged, so many tiny commits win nothing. `asks_done_reported` and `cost_usd_reported` are the side's own count: shown, not judged (`Metric.Info`). The fake worker writes the asked function, so the fake harness measures the pipeline's time and correctness. `HIVE_E2E_HARNESS=claude` makes it real work on real agents (plan usage) |
   | `recurse` | the child runs `hive gate --self-test`: the gate inside a child, gating a trivial change through a grandchild (its binary as both sides, so the right verdict is "not better"), on its own local org repos, which it must clean up. Inside the child's sandbox no sandbox is started, so the grandchildren run bare there, contained by the child's sandbox |

   More probes are added by name in `Config.Probe`; the live probes (`TestLive*`) are the e2e probes on a real harness.
5. **Decide.** `Decide` compares probe by probe and metric by metric. A probe the candidate passes less often than the control, or a metric worse beyond the noise, is a **regression**; the mirror is a **gain**, and so is each fix (step 1). Noise is the larger of 2% of the control's mean and twice the standard error of the difference of the two means, so more repeats tighten it. **Keep only if there is at least one gain and no regression.** On the daemon's runs this verdict is one thing a judge weighs, and the judge's call decides (step 6, docs/judge.md). A tie is a rollback; `--allow-tie` keeps a change that is meant to move nothing (a docs edit) when it breaks nothing, and the caller says so. Without it a docs edit is rolled back as "not better".
6. **Record.** `report.json` and `report.md` in the run's folder, a line in `gates.jsonl` beside it. Three outcomes, each with its own exit code:
   - **Kept** (exit 0).
   - **Rolled back** (exit 1). The candidate is worse, or it failed on its own before it could be measured: it does not build, fails its own vet or short tests where the control passes them (twice, named in the reason: `the candidate fails its own vet or short tests: internal/x TestY`), or rewrote its binary. The reason is appended to `--lessons` (`.hive/lessons.md`), where the next worker reads it. The reason is Decide's words or a fixed phrase, never the candidate's output.
   - **Could not run** (exit 3, `cant_run` in the report). The gate itself could not run or measure: no bubblewrap without `--allow-bare`, no Go, Yama off, an evaluator older than the outside measure, the meter or the org failing, out of time, the clone or the module download failing, the candidate's head conflicting with the base, the control not building, the build failing on both sides, vet or the short tests failing on both sides naming no test, or a probe that failed on both sides (that path was never measured). The report's `transient` marks a cause that may pass (a probe failing on both sides): the work module tries again after 10 minutes (`gateRetrySoon`), not the hour (`gateRetry`). Its `base_fails` marks a cause in the base itself: the control fails a step (its build, vet or the short tests), alone or with the candidate naming nothing. Every change at that base would build and test both sides only to fail alike, so the work module remembers it (`main_fails` on the verdict, kept from the journal across a restart) and runs no gate at that main for 6 hours (`gateRetryMain`); main moving ends it. Its `alone` marks a cause tied to this candidate alone (preparing the candidate's build, such as its own `go.mod`'s module download, or running out of time when the candidate's probes took longer than the control's, over the probes both ran (the candidate goes first, so an extra one of its own is left out); if the control was as slow, the machine is to blame): the candidate is still not judged, but other changes at the same base don't wait on it. This is not the candidate's failure, so **no lesson is written**: a check that can't find its own tool is "can't run", never red (see `.hive/lessons.md` on #111).

## Recursion and its caps

`--depth N` (default 1, at most `MaxDepth` = 2) is how many levels of gating the children may do; the child learns it as `HIVE_GATE_DEPTH` and `--self-test` refuses to run at 0. Each level makes at most 2 org repositories (the self-test uses local ones), and `--timeout` (default 2h) stops a run between probes.

## Installing a kept change, and going back

`hive gate ... --install <path>` installs only if the verdict is keep, the children ran under bubblewrap (a bare run is never installed), and the verified copy of the candidate's binary still has the sha256 taken right after the build, before any of its code ran, and the new install's `--version` names the version the gate stamped (`0.0.0-gate.<sha>`); a prebuilt binary has no stamped version and is never installed; a candidate that rewrote its own binary during the run is rolled back. Every report is signed: an HMAC over all of it, with a key the gate keeps in the person's config folder (`~/.config/hive/gate.key`, 0600), which no child sees. `hive gate install --report <run>/report.json --target <path>` installs a kept run later, through the same checks, and only from a report this machine's gate signed and nobody changed. A hand-written or edited report.json installs nothing. Anyone who can read the person's key could also just copy a binary into place, so the key guards against the children and agents, not against the person. Either way the install copies the current binary to `<path>.prev`, puts the new one in place, runs the health check (`--version` answers, and its last word is exactly the wanted version). The health check runs the new binary on the host, unsandboxed: it is the binary being installed, and **restores the previous binary if the check fails**. It does not touch the daemon's own updater (`internal/mod/release`), which keeps installing releases the way it did; wiring a gate in front of a release, and a health check after the updater's restart, is the next step.

## Where the sandbox is tested

ci's `sandboxed-e2e` job lifts Ubuntu's AppArmor user-namespace restriction and runs the gate's bubblewrap tests with `HIVE_GATE_BWRAP=1`, which turns their skip into a failure. The tests: the allowlist hides the host (`TestBwrapHidesTheHost`), the meter is the only way out and counts (`TestBwrapMeterIsTheOnlyWayOut`), sealed code runs in a sibling sandbox the gate starts on request, with no network and nothing of the side (`TestBwrapSealedCheckIsASibling`), the build and tests under bwrap (`TestBuild*`), a deadline kills a child's tree (`TestDeadlineKillsTheTree`), no sandbox starts inside another (`TestNoSandboxInsideASandbox`, which runs everywhere on Linux with a recording bwrap), and **a whole gate run** (`TestBwrapGateKeepsAndRollsBack`). That last one runs `Run` under real bubblewrap on a local org with the real probes: the daemon, the org round trip, the benchmark (inside each side's sandbox, its sealed check beside it, the meter as the only way out) and recurse. The keep run is a gate from commits: a trivial commit on a clone of this tree against the clone's head. The gate builds both (exact sha, stamped `0.0.0-gate.<sha>`, vet and short tests in the sandbox), judges them with the base's suite, which it compiles itself, and keeps the change with `--allow-tie`. The rollback run hands it a broken prebuilt candidate, which is rolled back with its lesson written. Both leave the org empty. A probe that fails on both sides is not an even result: that path was never measured, so the run could not decide (could not run). Its log in ci is the end-to-end record. Elsewhere they skip.

## On every change to the Hive itself

Only a clear fix skips the gate (issues #494, #568). Every task is taken as a gain unless its brief (`hive agent brief --aim fix --why "the failure"`) or its worker or the lead (`hive agent aim --aim fix|gain --why "..."`, journaled on the task) says it is a fix and names the failure it fixes (a bug, a failing test, a broken path); a task that says neither, a behaviour or feature change included, is unclear and taken as a gain, so it goes through the gate and leans on the score. Reverts are fixes. A fix merges on its tests, reads and the forge's checks, as in any project. The score measured on main after the merge doesn't revert a fix for a dip alone: the fix is kept, its score becomes the baseline, and a brief looks into the dip, whose worker reverts the fix only on judging that the fix itself made things worse; red tests after the merge still revert it (improve module). The task shows which it was taken as and why: the control center's task view (`aim`), `hive agent status` (`a fix` or `taken as a gain`), the task's log and the worker's brief. Turning a gain into a fix while its gate runs cancels that run, so the one gate slot frees for the gains behind it; the cancelled run records no verdict. A worker whose gain the gate rolled back can't make it a fix on its own word (only the lead can), so a change can't move its own bar. Since the aim is declared, the reader of a self fix is asked to flag one that is really aimed at a gain (a target to beat, or the benchmark, score or gate tuned to move a number), and the worker then declares it.

A self project's pull request (the Hive's own repository) aimed at a gain merges only on the gate's keep (`internal/mod/work/selfgate.go`, issue #361). Once its tests, reads and the forge's checks pass, the daemon runs `hive gate` on the PR's exact head, merged with main, against main as the merge sees it, from its own binary on this host, so the children's bubblewrap sandboxes start one level deep, beside each other (never inside an agent's sandbox, which this host's AppArmor refuses). It never passes `--allow-bare`.

- **The judge** (docs/judge.md): a verdict that measured both sides, keep or rollback, goes to a judge on another model than the worker's, which reads the brief, the worker's account, the diff and the report, and decides; the numbers are one thing it weighs. A candidate that failed before it was measured is rolled back without one.
- **Keep**: it merges. `core.Effects.Merge` refuses a self project's merge aimed at a gain (`MergeRequest.Gain`) without a keep for exactly that head and main (`Effects.Kept`: the judge's call, `judge.decided`, on a measured verdict, else the gate's own, `gate.judged`), so a main that moves means a new run.
- **Rolled back**: the change goes back to its worker as a fix round, with the report in `$HIVE_RUN/gate-report.md`, the judge's reasons when it decided, and the lesson line to add to `.hive/lessons.md`. The gate (or, for a measured verdict, which the daemon runs with `--judged`, the judge's rollback) also writes the lesson to `.hive/gates/<project>/recursive/lessons.md` on this machine, and the next brief quotes it until main's lessons name the same commit.
- **Conflicts with main** (could not run, with `conflicts`): the change goes back to its worker to merge main, as any conflict with main does (`$HIVE_RUN/main.bundle`); not a rollback, no lesson, no alert, and it holds no other change at that main. The gate runs again on the new head.
- **Could not run** (no bubblewrap, no Go, out of time, no report): the PR waits as it is, never merged unjudged, with one alert; the gate tries again after an hour. Until then other self PRs at the same main wait too, since they would fail the same way, unless the cause was that PR's alone (`alone`: its own build preparation, or out of time with the candidate the slower side). The daemon killing a gate that overran its own clock is not `alone`. Such a PR holds nobody, so one bad candidate can't starve the rest. When main itself fails in the gate (`main_fails`) and a held PR changes the gate's own code (`internal/gate/`, the `selfgate.go` files, `cmd/hive/gate.go`), the person gets **one** Waiting item, per project, to land it: the gate can't judge its own fix. "merge" lands that exact head without the gate's verdict (an approval `Effects.Merge` accepts in place of a keep, for that sha alone); the score measured after the merge still reverts it if main got worse. The item follows the PR to a new head, and closes by itself once the gate judges again.
- An improvement must show a clear gain: the daemon never passes `--allow-tie`, for prose or code alike (a revert is a fix, and never gated).
- One gate runs at a time; others wait their turn (`waiting for the recursive gate…`, which the stall watcher leaves alone). Each run gets `--timeout 2h`, and the daemon kills it 15 minutes past that; on Linux it dies with the daemon, and its sandboxes with it.
- Every verdict goes on the PR as a comment with the report, on the task (the control center's task view shows `gate` and `report`), and in the run's folder `.hive/gates/<project>/recursive/<run>/` (`report.md`, `report.json`, `gate.log`).
- The org: with both `/home/hive/h0-org.token` (the org's own, `core.OwnerTokens`) and `/home/hive/h0-gate.token` (the children's contents-only token), the gate runs with `--org Hive-RSI-Lab`, but only after `CheckReach` passes on the children's token. While `Hive-RSI-Lab/hive` (or any non-gate repository) is writable with that token, as probed with the token itself, it refuses; the gate then runs on a local org and the PR and an alert say what the owner must move: transfer or delete those repositories, or mint the children's token without write on them.

## What is not yet done

- Whether the control has a package is decided by its folder (a `.go` file in it). A package the control has only under a build tag that doesn't apply counts as present, so a failure there goes to the control rerun and, naming nothing, gives a transient could-not-run, not a rollback.
- Shared failures are matched by name from the candidate's own `go test -json` output, which its tests can write into (test2json reads what a test prints). When main already fails a test, a candidate's test could print a fake `--- FAIL` line with that name and a fake `--- PASS` for itself, making its own failure look like the shared one. The gate doesn't cross-check the names against the control's list of tests. What holds is that the probes still run on the candidate's binary, judged by the evaluator.

- A fix is judged by the candidate's own test, in the candidate's sandbox: the coverage profile is written by its test process, so a determined candidate could forge it. What holds is that the test is the same code on both sides and must fail on the control, every time, in either order; a change only to constants or declarations covers no statement and earns no fix. Nor is the control's failure checked to come from the touched code's result: a test that calls a changed function and then fails on something only the candidate's tree has (`os.Stat` of a file the change adds) meets every condition without forging anything. A reader of the change sees such a test; the gate does not.

- The release path does not run the gate: a kept merge releases as before.
- A machine without a Go toolchain cannot gate.
- The benchmark is four asks. A real harness inside the allowlisted sandbox also needs the `claude` CLI and its login bound in, which the gate does not do yet. Cost is the bytes through the meter, not tokens: it tracks what a model costs (context sent, output received) but not price or cache discounts. A bare run has no meter it can enforce.
- Org runs need a test-only org and a fine-grained child token on it (both the person's to make) and the per-owner token (brief 261024-015755-a3f383a160); no org run has been made yet: every daemon run on the tower so far used a local org.
- The evaluator's scratch folder (`TMPDIR`, under the side's root) is writable by the side while a run goes on, because it holds the workspaces and forges the evaluator hands the side. The side can change what the evaluator keeps there. What is judged doesn't come from there: the forge is read through the side's own sandbox, the landed code runs sealed from source on stdin, and the answers and the clock are the evaluator's.
- The evaluator, the side and the grandchild are the same uid; the separation is namespaces, mounts and Yama, not users. The evaluator shares the side's sandbox: the side cannot reach into it (see above), but it can signal it, which only fails the side's own run.
