# Briefing a worker

A worker knows only what its brief says, and you see only the account it sends back. The brief is your one lever on what comes back, so write it for a capable peer:

- **The goal**: what the work is for, in the person's words where you have them.
- **The bounds**: which project, what is in and what is out, what not to touch.
- **What done is**: a check someone else can run ("the tests pass and the new page shows the score"), not a feeling.
- **What you already know**: findings, dead ends and the files that matter, so it doesn't redo your reading.

Leave out edit steps and commands to type; a good worker finds its own route. If you can't write the brief clearly, you don't understand the task well enough to hand it off.

Pick the cheapest way that holds: do it yourself when it's a few steps you already know; spawn a helper (`hive agent spawn`) for bounded research inside your own run; file a brief (`hive agent brief`) for work that needs its own branch, review and merge.

Don't hand a worker your conclusion to confirm. When you want an independent read, give it the code and the question.
